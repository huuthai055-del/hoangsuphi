## 1. CACHE & QUEUE LAYER (REDIS CLIENT)

---

### 1.1 Mục tiêu

- **Tách biệt mối quan tâm (Namespace Isolation):** Đảm bảo dữ liệu cache, session, rate-limiting và queue không bị ghi đè lẫn nhau bằng cách định nghĩa các key namespace chuẩn hóa.
- **Quản lý kết nối bền bỉ:** Tự động kết nối lại khi Redis gặp sự cố (Auto-reconnection với exponential backoff), không làm crash server backend.
- **Tối ưu hóa tài nguyên:** Sử dụng connection pooling cho các tác vụ pub/sub hoặc job queue, tái sử dụng các kết nối thông thường.
- **Chống Race Condition:** Cung cấp cơ chế khóa phân tán (Distributed Locking - Redlock) để bảo vệ các tài nguyên quan trọng chống ghi trùng lặp (ví dụ: tạo transaction, booking request).
- **Health check tích hợp:** Phục vụ giám sát hệ thống thời gian thực với độ trễ (latency) của Redis.

---

### 1.2 Thiết kế

Chúng ta sử dụng thư viện `ioredis` - client Redis giàu tính năng nhất trong hệ sinh thái Node.js/Bun, hỗ trợ tốt Sentinel, Cluster và các cơ chế pipeline/transaction.

#### 1. Khởi tạo Redis Client: `apps/backend/src/lib/redis/client.ts`

```typescript
import Redis from 'ioredis'
import { env } from '@/config/env'
import { logger } from '@/lib/logger'

// Cấu hình reconnect backoff strategy
const retryStrategy = (times: number) => {
  const delay = Math.min(times * 50, 2000)
  logger.warn({ retryAttempt: times, nextDelayMs: delay }, '🔌 Redis reconnecting...')
  return delay
}

// Khởi tạo Redis Instance chính (dùng cho Cache, Session, Rate Limit)
export const redis = new Redis(env.REDIS_URL, {
  keyPrefix: env.REDIS_KEY_PREFIX,
  maxRetriesPerRequest: 3,
  enableReadyCheck: true,
  retryStrategy,
})

redis.on('connect', () => logger.info('🔌 Redis connection established'))
redis.on('ready', () => logger.info('🔌 Redis client ready to use'))
redis.on('error', (err) => logger.error({ err: err.message }, '❌ Redis connection error'))
redis.on('close', () => logger.warn('🔌 Redis connection closed'))

// Khởi tạo Connection riêng cho Queue (BullMQ yêu cầu connection độc lập)
let queueRedisConnection: Redis | null = null

export function getQueueRedisConnection(): Redis {
  if (!queueRedisConnection) {
    queueRedisConnection = new Redis(env.REDIS_URL, {
      maxRetriesPerRequest: null, // BullMQ khuyến nghị set null
      enableReadyCheck: false,
      retryStrategy,
    })
  }
  return queueRedisConnection
}

// Export type dùng cho Dependency Injection
export type RedisClient = Redis

// ─── Standard TTL Policy (Bảng TTL chuẩn) ────────────────────────────────────
export const TTL_POLICY = {
  region: 60 * 60 * 24,       // 24h
  business: 60 * 15,          // 15m
  weather: 60 * 10,           // 10m
  search: 60 * 5,             // 5m
  review: 60 * 5,             // 5m
  homepage: 60 * 30,          // 30m
  session: 60 * 60 * 24 * 30, // 30 days
} as const

// ─── Cache Helpers (Chuẩn hóa Serialization & getOrSet) ──────────────────────
export const cache = {
  /**
   * Lấy dữ liệu và tự động deserialize
   */
  async get<T>(key: string): Promise<T | null> {
    try {
      const data = await redis.get(key)
      if (!data) return null
      return JSON.parse(data) as T
    } catch (error) {
      logger.error({ error, key }, '❌ Redis Cache get parse error')
      return null
    }
  },

  /**
   * Lưu dữ liệu kèm serialize tự động và TTL
   */
  async set<T>(key: string, value: T, ttlSeconds: number): Promise<boolean> {
    try {
      const serialized = JSON.stringify(value)
      const result = await redis.set(key, serialized, 'EX', ttlSeconds)
      return result === 'OK'
    } catch (error) {
      logger.error({ error, key }, '❌ Redis Cache set stringify error')
      return false
    }
  },

  /**
   * Pattern Cache-Aside: Lấy cache, nếu hụt thì gọi factory, ghi cache rồi trả về
   */
  async getOrSet<T>(
    key: string,
    ttlSeconds: number,
    factory: () => Promise<T>
  ): Promise<T> {
    const cached = await this.get<T>(key)
    if (cached !== null) {
      return cached
    }

    const freshData = await factory()
    await this.set(key, freshData, ttlSeconds)
    return freshData
  },

  /**
   * Xóa một key
   */
  async del(key: string): Promise<boolean> {
    const result = await redis.del(key)
    return result > 0
  }
}

```

#### 3. Thiết kế Distributed Lock Helper: `apps/backend/src/lib/redis/lock.ts`

```typescript
import { redis } from './client'
import { CacheKeys } from './keys'
import { logger } from '@/lib/logger'

interface LockOptions {
  ttlMs?: number      // Thời gian khóa tự động giải phóng (tránh deadlock)
  timeoutMs?: number  // Thời gian chờ để lấy khóa trước khi fail
  retryDelayMs?: number
}

export async function acquireLock(
  resource: string,
  token: string, // UUID định danh tiến trình nắm giữ khóa
  options: LockOptions = {}
): Promise<boolean> {
  const { ttlMs = 5000, timeoutMs = 2000, retryDelayMs = 100 } = options
  const key = CacheKeys.lock(resource)
  const start = Date.now()

  while (Date.now() - start < timeoutMs) {
    // NX: Chỉ set nếu key chưa tồn tại, PX: set TTL miliseconds
    const result = await redis.set(key, token, 'NX', 'PX', ttlMs)
    if (result === 'OK') {
      return true
    }
    // Chờ trước khi retry
    await new Promise((resolve) => setTimeout(resolve, retryDelayMs))
  }
  
  logger.warn({ resource }, '⚠️ Failed to acquire lock')
  return false
}

export async function releaseLock(resource: string, token: string): Promise<boolean> {
  const key = CacheKeys.lock(resource)
  // Sử dụng Lua Script để đảm bảo nguyên tử (atomic): chỉ xóa khóa nếu giá trị trùng khớp với token nắm giữ
  const luaScript = `
    if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
    else
      return 0
    end
  `
  const result = await redis.eval(luaScript, 1, key, token)
  return result === 1
}
```

#### 4. Enterprise Health Check: `apps/backend/src/lib/redis/health.ts`

```typescript
import { redis } from './client'
import { logger } from '@/lib/logger'

export async function redisHealthCheck(): Promise<{ status: 'healthy' | 'unhealthy'; latencyMs: number; error?: string }> {
  const start = performance.now()
  try {
    const response = await redis.ping()
    const latencyMs = Math.round(performance.now() - start)
    
    if (response === 'PONG') {
      return { status: 'healthy', latencyMs }
    }
    throw new Error(`Unexpected ping response: ${response}`)
  } catch (err: any) {
    logger.error({ error: err.message }, '❌ Redis health check failed')
    return {
      status: 'unhealthy',
      latencyMs: Math.round(performance.now() - start),
      error: err.message,
    }
  }
}
```

### 1.3 Lý do lựa chọn

| Quyết định thiết kế | Lý do lựa chọn |
|:---|:---|
| **ioredis** | Khác với `node-redis`, `ioredis` hỗ trợ mạnh mẽ Cluster, Sentinel, Pipeline và có cơ chế xử lý reconnection backoff ưu việt hơn, đồng thời là driver được BullMQ chọn lựa làm nền tảng. |
| **Lua Script cho Release Lock** | Bảo vệ tính nguyên tử (atomic) của khóa. Nếu không dùng script, một thread A có thể vô tình xóa khóa của thread B nếu khóa của thread A đã hết hạn trước khi thread A gọi lệnh xóa. |
| **Tách biệt Connection cho Queue** | BullMQ chiếm dụng luồng (blocking commands như BRPOPLPUSH), do đó bắt buộc phải sử dụng một connection Redis độc lập để không làm nghẽn các tác vụ đọc/ghi cache thường ngày. |
| **Key Factory** | Đảm bảo tính nhất quán của namespace, tránh rủi ro trùng lặp key (cache stampede) và giúp dev dễ tìm kiếm/quản lý key. |

### 1.4 Ưu điểm

- **Khả năng phục hồi cao (Resiliency):** Cơ chế retry thông minh ngăn chặn server sập khi Redis restart tạm thời hoặc rớt mạng.
- **Tính an toàn tuyệt đối:** Distributed Lock ngăn chặn race condition tại tầng ứng dụng mà không cần lock database level (vốn gây nghẽn DB nặng nề).
- **Hộp đen cấu hình (Encapsulation):** Khai báo tập trung keys giúp việc thay đổi cấu trúc prefix hay prefix pattern không ảnh hưởng đến logic của Service.

---

### 1.5 Nhược điểm

- **Distributed Lock đơn lẻ:** Thiết kế khóa trên một node Redis (Single instance lock). Nếu Redis chạy cluster, cần nâng cấp lên thư viện `redlock` để thực hiện khóa trên đa số nodes (Quorum lock). Tuy nhiên, đối với Phase 2 và 3, thiết kế hiện tại là quá đủ và tối ưu tài nguyên.

---

### 1.6 Các lựa chọn khác đã xem xét

| Phương án | Vấn đề |
|:---|:---|
| **node-redis** | Thiếu hỗ trợ pipeline nâng cao, cấu hình retry kém linh hoạt hơn ioredis trong các môi trường phức tạp. |
| **Memcached** | Không hỗ trợ cấu trúc dữ liệu phong phú (Hashes, Sets, Sorted Sets) và không có pub/sub hay job queue capability, không phù hợp cho cả cache lẫn queue. |
| **Lock bằng Database (SELECT FOR UPDATE)** | Gây block connection pools của PG, giảm khả năng chịu tải của DB khi traffic cao. |

---

### 1.7 Vì sao không chọn

- **node-redis:** Dù nhẹ hơn, nhưng khi mở rộng sang các hệ thống Queue chạy nền (như BullMQ trong Phase 4), `ioredis` là sự bắt buộc được khuyến nghị từ phía nhà phát triển BullMQ. Chọn `ioredis` ngay từ đầu giúp giảm rủi ro refactor driver ở các Phase sau.
- **Lock bằng Database:** Khi Homestay hoặc Điểm tham quan ở Hoàng Su Phì đón nhận lượt truy cập lớn vào tháng 9 (mùa lúa chín), việc lock DB sẽ nhanh chóng làm đầy PgBouncer connection queue, khiến toàn bộ website bị nghẽn (dù là trang tin tức tĩnh). Khóa phân tán trên Redis (chạy hoàn toàn trên RAM) giải quyết bài toán này với tốc độ sub-milisecond.

---

### 1.8 Khả năng mở rộng

- **Redis Cluster / Sentinel Support:** Khi cấu hình production nâng cấp lên Redis Cluster, client chỉ cần khai báo lại constructor mà không cần sửa code ứng dụng:
  ```typescript
  export const redis = new Redis.Cluster([{ host: 'node1' }, { host: 'node2' }])
  ```
- **Pipeline & Transaction:** `ioredis` cho phép gom nhóm các lệnh write thông qua `.pipeline()` giúp tối ưu hóa số lượng network roundtrips lên đến 80-90% cho các tác vụ ghi log/analytics hoặc cache tập lớn.

---

### 1.9 Best Practices

- **Bắt buộc có TTL:** Mọi dữ liệu cache ghi vào Redis qua hàm `set` phải đi kèm giá trị TTL (Time To Live). Tuyệt đối không lưu cache vô hạn (chỉ trừ session được quản lý vòng đời chặt chẽ).
- **Prefix nhất quán:** Prefix của key luôn phân tách bằng dấu hai chấm `:` để các GUI Tool quản lý Redis (như RedisInsight) tự động phân nhóm thư mục trực quan.
- **Redact secrets:** Tránh đưa các payload dữ liệu nhạy cảm của người dùng (như password hash, raw credentials) vào cache trừ khi được mã hóa bổ sung.
