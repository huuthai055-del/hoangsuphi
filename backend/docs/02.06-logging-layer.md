## 1. LOGGING & OBSERVABILITY LAYER

---

### 1.1 Mục tiêu

- **Structured Logging (Ghi log có cấu trúc):** Xuất toàn bộ log ở định dạng JSON để các Log Aggregators (ELK, Grafana Loki, Datadog) dễ dàng index và lọc theo thuộc tính mà không cần Regex phức tạp.
- **Zero-leak Security (Bảo vệ thông tin nhạy cảm):** Tự động che giấu (redact) các thông tin nhạy cảm như `password`, `token`, `authorization`, `refreshToken`, `email` để tránh vi phạm các quy định bảo mật.
- **Distributed Request Tracing (Dấu vết yêu cầu phân tán):** Tích hợp `requestId` vào toàn bộ log phát sinh trong cùng một luồng request (sử dụng `AsyncLocalStorage`), giúp map vết lỗi (troubleshooting) tức thì.
- **Tách biệt môi trường (Pretty-print in dev):** Log ở dạng dòng text màu sắc, dễ đọc ở local development nhưng tự động chuyển sang JSON nén ở Production để tối ưu hiệu năng I/O.
- **Tối ưu hóa hiệu năng I/O:** Sử dụng Pino với cơ chế asynchronous logging khi tải cực đại, tránh việc ghi file đồng bộ gây chậm (blocking) event loop.

---

### 1.2 Thiết kế

Chúng ta xây dựng logger dựa trên Pino - logger nhanh nhất cho Node.js/Bun, kết hợp với `AsyncLocalStorage` để lưu trữ Request Context.

#### 1. Khởi tạo Request Context Store: `apps/backend/src/lib/logger/context.ts`

Sử dụng `AsyncLocalStorage` để lưu trữ và truyền dẫn `requestId` xuyên suốt các lớp logic mà không cần truyền tham số thủ công.

```typescript
import { AsyncLocalStorage } from 'async_hooks'

export interface RequestStore {
  requestId: string
  userId?: string
}

export const requestStore = new AsyncLocalStorage<RequestStore>()
```

#### 2. Khởi tạo Pino Logger: `apps/backend/src/lib/logger.ts`

```typescript
import pino from 'pino'
import { env, isDev } from '@/config/env'
import { requestStore } from './logger/context'

// Danh sách các key nhạy cảm cần tự động ẩn (redact)
const redactPaths = [
  'req.headers.authorization',
  'req.headers.cookie',
  'req.body.password',
  'req.body.token',
  'req.body.refreshToken',
  'req.body.accessToken',
  'password',
  'token',
  'refreshToken',
  'accessToken',
]

// Khởi tạo logger instance
export const logger = pino({
  level: env.LOG_LEVEL,
  redact: {
    paths: redactPaths,
    censor: '[REDACTED]',
  },
  // Sử dụng AsyncLocalStorage để tự động chèn requestId vào log metadata
  mixin() {
    const store = requestStore.getStore()
    return store ? { requestId: store.requestId, userId: store.userId } : {}
  },
  // Cấu hình output format
  transport: isDev
    ? {
        target: 'pino-pretty',
        options: {
          colorize: true,
          ignore: 'pid,hostname',
          translateTime: 'SYS:yyyy-mm-dd HH:MM:ss',
        },
      }
    : undefined, // Production xuất JSON mặc định ra stdout
})

// Chế độ ghi log bất đồng bộ cho production (tối ưu hóa hiệu năng)
// Nếu deploy trên môi trường chịu tải rất cao, ta sẽ dùng:
// export const logger = pino(pino.destination({ sync: false }))
```

#### 3. Middleware Ghi vết & Request-ID: `apps/backend/src/middleware/logger.middleware.ts`

Tạo request-id và quản lý vòng đời ghi log của request trong Hono.

```typescript
import type { MiddlewareHandler } from 'hono'
import { crypto } from 'bun' // Sử dụng Bun native crypto helper sinh UUIDv4 nhanh
import { logger } from '@/lib/logger'
import { requestStore } from '@/lib/logger/context'

export const loggerMiddleware = (): MiddlewareHandler => {
  return async (c, next) => {
    // 1. Trích xuất hoặc khởi tạo requestId & correlationId từ Headers (hỗ trợ upstream gateways)
    const correlationId = c.req.header('x-correlation-id') || c.req.header('x-request-id') || crypto.randomUUID()
    const requestId = c.req.header('x-request-id') || crypto.randomUUID()
    
    // Set headers trả về cho client
    c.res.headers.set('x-request-id', requestId)
    c.res.headers.set('x-correlation-id', correlationId)

    // 2. Wrap request vào AsyncLocalStorage
    return requestStore.run({ requestId }, async () => {
      const start = performance.now()
      const { method, url } = c.req
      
      logger.info({
        req: {
          method,
          url,
          headers: c.req.header(),
          correlationId,
          // Body chỉ log trong môi trường development để tránh tốn tài nguyên ở prod
          body: env.NODE_ENV === 'development' ? await c.req.valid('json').catch(() => undefined) : undefined,
        }
      }, `📥 HTTP ${method} ${url} started`)

      try {
        await next()
      } catch (err: any) {
        logger.error({
          err: {
            message: err.message,
            stack: err.stack,
          },
          correlationId
        }, `❌ HTTP ${method} ${url} failed`)
        throw err
      } finally {
        const durationMs = Math.round(performance.now() - start)
        const status = c.res.status
        const memoryUsage = process.memoryUsage().heapUsed

        // Ghi nhận Performance Metrics cùng Log HTTP response
        logger.info({
          res: {
            status,
            durationMs,
            metrics: {
              memoryHeapUsedBytes: memoryUsage,
            }
          },
          correlationId
        }, `📤 HTTP ${method} ${url} finished - ${status} (${durationMs}ms)`)
      }
    })
  }
}


// Cấu hình Audit Logger riêng biệt
// Dành riêng cho việc ghi log kiểm toán nghiệp vụ (không lẫn vào application logs)
export const auditLogger = logger.child({ type: 'audit' })

// Child Logger pattern khuyến khích cho các services
// Ví dụ: const serviceLogger = logger.child({ module: 'UserService' })

### 1.3 Lý do lựa chọn

| Quyết định thiết kế | Lý do lựa chọn |
|:---|:---|
| **Pino Logger** | Logger nhanh nhất cho JavaScript/TypeScript (nhanh hơn Winston 5x, nhanh hơn console.log 10x). Có cơ chế mixin tích hợp sẵn để luồn lách dữ liệu context mà không ảnh hưởng tới API gọi log. |
| **AsyncLocalStorage** | Giải pháp chuẩn của Node.js/Bun để truyền dẫn ngữ cảnh của thread xử lý mà không làm ô nhiễm chữ ký hàm (parameter pollution). Developer ở lớp Service chỉ cần viết `logger.info("message")`, `requestId` sẽ tự động được inject ở kết quả log. |
| **Pino Redaction** | Built-in module tối ưu hóa viết bằng C/C++ (ở gốc Pino), thực hiện lọc và thay thế chuỗi nhạy cảm nhanh hơn nhiều so với việc viết hàm JS đệ quy để map object body. |
| **Pino Pretty** | Chỉ bật ở môi trường phát triển (dev) vì pino-pretty chạy trên luồng phụ và tốn I/O. Tắt hoàn toàn ở production để tối đa hóa throughput. |

---

### 1.4 Ưu điểm

- **Khả năng quan sát cao (Observability):** Khi hệ thống gặp lỗi ở môi trường production, chỉ cần copy `requestId` từ API Response của khách hàng và dán vào thanh tìm kiếm Grafana Loki là có thể xem toàn bộ hành trình đi qua DB, Redis và các micro-services liên quan.
- **Hiệu năng vượt trội:** Không gây nghẽn Event Loop nhờ cơ chế stringify siêu tốc của Pino.
- **An toàn thông tin:** Tránh tuyệt đối việc vô tình ghi đè token, password của khách hàng vào file log trên server (vốn là lỗi phổ biến ở các hệ thống không có redaction chuẩn).

---

### 1.5 Nhược điểm

- **Mất mát log khi crash (nếu dùng async destination):** Nếu bật chế độ async log destination (`sync: false`) để đạt hiệu năng tối đa, khi máy chủ bị mất điện đột ngột hoặc container bị kill, các log nằm trong buffer (khoảng vài chục KB) chưa kịp ghi ra stdout sẽ bị mất. Đối với dự án CMS du lịch, ta chọn cấu hình ghi log đồng bộ mặc định của Pino để an toàn dữ liệu, chỉ nâng cấp lên async khi có traffic khổng lồ.

---

### 1.6 Các lựa chọn khác đã xem xét

| Phương án | Vấn đề |
|:---|:---|
| **Winston** | Rất phổ biến nhưng hiệu năng kém (chậm hơn Pino 5x), cú pháp cấu hình Transport rườm rà. |
| **Bun.write / Console.log** | console.log là hàm đồng bộ (blocking I/O). Sử dụng console.log trong production sẽ làm chậm luồng xử lý chính của Hono lên đến 30-50% dưới tải nặng. |
| **Truyền `requestId` thủ công** | Đòi hỏi mọi service method phải nhận biến `ctx` hoặc `requestId`. Gây xấu code, khó maintain và dễ quên truyền tham số. |

---

### 1.7 Vì sao không chọn

- **Console.log:** Ghi log đồng bộ. Khi server nhận 1000 req/s, console.log sẽ chặn (block) thread để ghi ra stdout, khiến hàng trăm request khác phải chờ đợi I/O kết thúc.
- **Winston:** Winston sử dụng nhiều hàm JS trung gian để format log, tiêu tốn nhiều CPU cycles cho việc định dạng string, điều này đi ngược lại tiêu chí tối ưu hóa của Hono & Bun.

---

### 1.8 Khả năng mở rộng

- **Log Aggregators:** Ở Phase 10 (Deployment), stdout của Docker container sẽ được thu gom tự động bằng **Promtail** (hoặc Logstash) để đẩy lên **Grafana Loki** hoặc **Elasticsearch**, không cần ứng dụng phải viết code gửi API đẩy log.
- **Audit Logs Table:** Đối với các log mang tính chất nghiệp vụ bắt buộc lưu trữ dài hạn (như lịch sử thay đổi nội dung bài viết, sửa giá homestay), hệ thống sẽ không ghi ra stdout thông thường mà sẽ Insert trực tiếp vào bảng `audit_logs` của PostgreSQL (sử dụng Service riêng).

### 1.9 Best Practices

- **Log Levels chuẩn hóa:**
  - `trace`: Log chi tiết hoạt động nội bộ sâu (ví dụ: bắt đầu vòng lặp, chi tiết chuyển mã dữ liệu).
  - `debug`: Dành cho nhà phát triển gỡ lỗi (SQL query raw, Redis cache hit/miss payload).
  - `info`: Ghi nhận luồng xử lý thành công tiêu biểu (ví dụ: `User login`, `Database migration complete`).
  - `warn`: Cảnh báo nguy cơ không gây dừng chương trình (ví dụ: `Rate limit exceeded`, `Slow query detected`).
  - `error`: Lỗi xử lý nghiệp vụ hoặc lỗi hệ thống có thể phục hồi (ví dụ: `Database timeout`, `Auth token expired`).
  - `fatal`: Lỗi hệ thống cực kỳ nghiêm trọng buộc app crash/stop (ví dụ: `Out of memory`, `Port already in use`).
- **Sử dụng Child Logger cho từng Module:** Khuyến khích khởi tạo logger cho từng component/class để dễ theo dõi nguồn gốc phát sinh log:
  ```typescript
  const serviceLogger = logger.child({ module: 'UserService' })
  serviceLogger.info({ userId }, 'User status updated')
  ```
- **Tách biệt Application Log và Audit Log:**
  - Application logs (sử dụng `logger` mặc định) ghi nhận trạng thái kỹ thuật và luồng request của hệ thống.
  - Audit logs (sử dụng `auditLogger`) ghi nhận các hành động nghiệp vụ quan trọng phục vụ kiểm toán bảo mật (như: thay đổi quyền người dùng, admin xóa bài viết, cấu hình hệ thống bị đổi). Audit logs luôn được export riêng biệt sang DB hoặc cold-storage.
- **Không dùng string concatenation:**
  - ❌ `logger.info("User " + user.id + " logged in")`
  - ✅ `logger.info({ userId: user.id }, "User logged in")` (Giúp Log Search Engine index thuộc tính `userId`).
- **Sẵn sàng cho OpenTelemetry (OTEL Reservation):** Các log entry được cấu trúc hóa chặt chẽ dưới dạng JSON với `requestId` và `correlationId` làm metadata. Ở các Phase sau, ta chỉ cần gắn thêm OTEL Pino Transport hoặc SDK OpenTelemetry để tự động xuất log trace context (TraceParent/SpanContext) mà không phải thay đổi bất kỳ cú pháp gọi log nào trong codebase.
