## 1. PURPOSE
Tài liệu này đặc tả chi tiết thiết kế CSDL (Database Schema) và chiến lược di chuyển dữ liệu (Migration Strategy) cho **Phase 4.3 — Media Upload Production Pipeline**. ## 2. APPROVED PREREQUISITES FROM 4.3.0
Các quyết định kiến trúc đã được phê duyệt ở Step 4.3.0 ảnh hưởng trực tiếp đến schema thiết kế bao gồm:
1. **Unbound Upload (AD-MEDIA-011)**: Client không truyền `ownerType` và `ownerId` khi upload. Mọi tệp tải lên ban đầu đều ở trạng thái unbound (`ownerType = null`, `ownerId = null`).
2. **Deduplication HTTP Status (AD mở 1)**: Phát hiện trùng lặp ảnh khớp đúng uploader context ở trạng thái `READY` sẽ trả về `200 OK` kèm cờ `meta.deduplicated = true`.
3. **Soft-delete (AD mở 2)**: Lệnh xóa chỉ đánh dấu xóa mềm DB (`deleted_at` không null); dọn dẹp vật lý trên Cloudinary được xử lý ngầm định kỳ bằng command scheduler hằng ngày với retention 30 ngày (không dùng BullMQ/Queue/worker in-process). URL Cloudinary cũ vẫn có thể truy cập được thông qua CDN cho tới khi bị purge.
4. **EXIF/GPS removal (AD-MEDIA-009)**: Triệt để loại bỏ siêu dữ liệu nhạy cảm khỏi tệp ảnh nhị phân xuất bản (cấm gọi `.withMetadata()` / `.keepMetadata()`).
5. **Sanitized Master (AD-MEDIA-012)**: Lưu trữ ảnh master đã được nén WebP và strip sạch EXIF, thay thế tệp thô ban đầu.

## 6. TARGET SCHEMA PRINCIPLES
Chiến lược cập nhật schema của Phase 4.3 tuân thủ các nguyên tắc:
1. **Chỉ thêm, không xóa (Additive only)**: Không xóa các trường cũ như `storage_key` hay `hash` ở bảng `media` để đảm bảo code cũ Phase 3.7 không bị sập.
2. **Nullable cho các trường mới hoặc có Default**: Cột mới thêm `storage_provider` có giá trị mặc định là `'LOCAL'` để các bản ghi cũ tự động tương thích. Các trường `alt_text` và `caption` là nullable.
3. **Database-level Constraint**: Bắt buộc khóa chặt các ràng buộc về tính duy nhất ở mức CSDL để bảo vệ chống race condition.

## 7. STORAGE PROVIDER DESIGN
- **Vị trí lưu trữ**: Thêm cột `storage_provider` trực tiếp vào bảng `media`.
- **Kiểu dữ liệu**: `varchar(50)`
- **Giá trị mặc định**: `'LOCAL'` (để các bản ghi cũ tự động map với Local storage).
- **Allowlist Check Constraint**: `CHECK (storage_provider IN ('LOCAL', 'CLOUDINARY'))`.
- **Lý do**: Toàn bộ tệp Sanitized Master và các variants của một Media luôn được lưu trữ nhất quán trên cùng một nhà cung cấp trong Phase 4.3. Không hỗ trợ mixed-provider.

## 8. STORAGE KEY / PROVIDER ASSET DESIGN
- DB chỉ lưu `storage_key` đóng vai trò là provider-neutral logical object key (đồng thời là Cloudinary `public_id`).
- Định dạng lưu trữ:
  - Sanitized Master: `hoangsuphi/{env}/media/{mediaId}/master`
  - Variants: `hoangsuphi/{env}/media/{mediaId}/{variant_type}`
- URL công khai không được lưu cứng vào DB để tránh trôi lệch cấu hình CDN. URL sẽ luôn được sinh động thông qua `IMediaStorage.getUrl(storage_key)`.

## 11. SCOPED DEDUPLICATION & NULL OWNER SEMANTICS
- Vì Phase 4.3 áp dụng cơ chế **Unbound Upload** (mọi ảnh mới tạo đều có `owner_type = null` và `owner_id = null`), các index unique composite thông thường sẽ mất tác dụng chống ghi trùng trong PostgreSQL do giá trị `NULL` được đối xử là khác nhau (`NULL != NULL`).
- **Giải pháp**: Thiết lập một **Partial Unique Index** cho các ảnh unbound ở trạng thái hoạt động:
  ```sql
  CREATE UNIQUE INDEX "media_unbound_active_hash_unique_idx" ON "media" ("uploaded_by", "hash")
  WHERE "owner_type" IS NULL 
    AND "owner_id" IS NULL 
    AND "deleted_at" IS NULL 
    AND "status" IN ('UPLOADING', 'PROCESSING', 'READY');
  ```
- **Lý do & Lợi ích**:
  - Chặn đứng 100% race condition khi một người dùng gửi song song các request upload cùng một tệp ảnh. DB sẽ ném lỗi unique constraint, giúp tầng ứng dụng bắt lỗi và xử lý idempotent (trả về mã `200 OK` cho READY, hoặc `409` cho UPLOADING/PROCESSING).
  - Không cản trở người dùng khác upload cùng tệp ảnh (vì phân biệt theo `uploaded_by`).
  - Không cản trở việc tải lên lại tệp ảnh nếu bản ghi cũ đã bị xóa mềm (`DELETED`) hoặc bị chuyển sang `FAILED`.
- **Hỗ trợ truy vấn Scoped Dedup**: Tạo thêm index thường (non-unique index) hỗ trợ tìm kiếm nhanh scoped dedup cho cả các bản ghi có gắn bound owner (legacy/future bound uploads):
  `CREATE INDEX "media_scoped_hash_idx" ON "media" ("uploaded_by", "owner_type", "owner_id", "hash");`

## 12. DEDUP STATUS MATRIX (Hành vi mong đợi)

| Trạng thái của ảnh trùng trong DB | Cùng uploader/hash | Hành vi dự kiến | Phản hồi API | Tác động Constraint |
| :--- | :--- | :--- | :--- | :--- |
| `READY` (chưa xóa mềm) | Có | Trả về bản ghi sẵn có | `200 OK` + `meta.deduplicated = true` | Partial Unique Index chặn ghi mới |
| `UPLOADING` / `PROCESSING` | Có | Báo lỗi tài nguyên đang bận | `409 Conflict` | Partial Unique Index chặn ghi mới |
| `FAILED` | Có | Cho phép upload mới độc lập | `201 Created` (Tạo bản ghi mới) | Nằm ngoài Partial Index filter |
| `DELETED` (đã soft-deleted) | Có | Cho phép upload mới độc lập | `201 Created` (Tạo bản ghi mới) | Nằm ngoài Partial Index filter |

## 13. OWNER-PAIR CONSTRAINTS
Để tránh tình trạng dữ liệu mâu thuẫn (ví dụ: chỉ có `owner_type` mà không có `owner_id` hoặc ngược lại), thêm check constraint vào bảng `media`:
```sql
ALTER TABLE "media" ADD CONSTRAINT "media_owner_pair_check" CHECK (
  (owner_type IS NULL AND owner_id IS NULL)
  OR
  (owner_type IS NOT NULL AND owner_id IS NOT NULL)
);
```

## 18. LEGACY DATA STRATEGY
Khi thực thi migration trên CSDL đã có sẵn dữ liệu của Phase 3.7:
1. **Backfill `storage_provider`**: Cột `storage_provider` tự động nhận giá trị mặc định `'LOCAL'` cho toàn bộ các dòng hiện có.
2. **Bảo toàn dữ liệu cũ**: Các bản ghi cũ giữ nguyên `storage_key` dạng cục bộ và variants tương ứng.
3. **Legacy Hash Deduplication**: Các bản ghi cũ có `owner_type` và `owner_id` khác null sẽ không bị ảnh hưởng bởi Partial Unique Index mới (chỉ nhắm vào unbound uploads).

## 19. MIGRATION PHASES & RUNBOOK SEPARATION (Phân tách luồng di chuyển)

> [!IMPORTANT]
> **Quy tắc Rollout bắt buộc**: Để đảm bảo an toàn tuyệt đối trên production, chiến lược di chuyển được chia thành 2 phần độc lập:
> 1. **Transactional Migration File (Chạy qua Drizzle Runner)**: Chỉ chứa khối kiểm tra preflight chặn dữ liệu bẩn và các thay đổi cấu trúc bảng additive (add columns & constraints).
> 2. **Production Index Runbook (Thực thi thủ công ngoài Transaction)**: Chứa các lệnh tạo index concurrently. **Không được gộp các lệnh tạo index này vào file migration chính chạy qua transaction runner**.

### Phần 1: Transactional Migration File

#### Giai đoạn 1: Preflight Data Cleanup & Hard Gates (Bảo vệ dữ liệu)
Trước khi chạy lệnh thay đổi schema, migration script bắt buộc chạy khối lệnh SQL sau để kiểm tra dữ liệu cũ:
```sql
DO $$
BEGIN
  -- 1. Kiểm tra duplicate variants
  IF EXISTS (
    SELECT 1 FROM media_variants GROUP BY media_id, variant_type HAVING COUNT(*) > 1
  ) THEN
    RAISE EXCEPTION 'Preflight check failed: Duplicate variants detected in media_variants table. Please run the cleanup runbook script first.';
  END IF;

  -- 2. Kiểm tra duplicate metadata
  IF EXISTS (
    SELECT 1 FROM media_metadata GROUP BY media_id HAVING COUNT(*) > 1
  ) THEN
    RAISE EXCEPTION 'Preflight check failed: Duplicate metadata detected in media_metadata table. Please run the cleanup runbook script first.';
  END IF;

  -- 3. Kiểm tra active unbound duplicates (uploaded_by, hash)
  IF EXISTS (
    SELECT 1 FROM media 
    WHERE owner_type IS NULL AND owner_id IS NULL AND deleted_at IS NULL AND status IN ('UPLOADING', 'PROCESSING', 'READY')
    GROUP BY uploaded_by, hash 
    HAVING COUNT(*) > 1
  ) THEN
    RAISE EXCEPTION 'Preflight check failed: Duplicate active unbound media (uploaded_by, hash) detected in media table. Please run the cleanup runbook script first.';
  END IF;

  -- 4. Kiểm tra active unbound rows có uploaded_by IS NULL
  IF EXISTS (
    SELECT 1 FROM media 
    WHERE owner_type IS NULL AND owner_id IS NULL AND deleted_at IS NULL AND status IN ('UPLOADING', 'PROCESSING', 'READY') AND uploaded_by IS NULL
  ) THEN
    RAISE EXCEPTION 'Preflight check failed: Active unbound media rows with NULL uploaded_by detected. Please run the cleanup runbook script first.';
  END IF;

  -- 5. Kiểm tra owner pair lệch (một trong 2 trường null và trường còn lại không null)
  IF EXISTS (
    SELECT 1 FROM media 
    WHERE (owner_type IS NULL AND owner_id IS NOT NULL) OR (owner_type IS NOT NULL AND owner_id IS NULL)
  ) THEN
    RAISE EXCEPTION 'Preflight check failed: Invalid owner pairs detected (one of owner_type or owner_id is NULL). Please run the cleanup runbook script first.';
  END IF;
END $$;
```
*Lưu ý*: Khối preflight check này sẽ ném ngoại lệ (`RAISE EXCEPTION`) làm crash và rollback toàn bộ transaction của migration nếu phát hiện dữ liệu vi phạm, đảm bảo an toàn tuyệt đối cho hệ thống.

## 20. PRODUCTION INDEX RUNBOOK (Chạy ngoài transaction)

### Bước 1: Tạo index concurrently
Quản trị viên thực thi trực tiếp các lệnh SQL sau bằng psql/shell độc lập ngoài transaction block:
```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS "media_scoped_hash_idx" ON "media" ("uploaded_by", "owner_type", "owner_id", "hash");

CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS "media_unbound_active_hash_unique_idx" ON "media" ("uploaded_by", "hash")
WHERE "owner_type" IS NULL 
  AND "owner_id" IS NULL 
  AND "deleted_at" IS NULL 
  AND "status" IN ('UPLOADING', 'PROCESSING', 'READY');

CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS "media_variants_media_id_variant_type_unique_idx" ON "media_variants" ("media_id", "variant_type");

CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS "media_metadata_media_id_unique_idx" ON "media_metadata" ("media_id");
```

### Bước 2: Xác minh tính hợp lệ và cấu trúc của Index (Catalog Verification)
Để đảm bảo các index được tạo thành công, không bị bỏ qua lỗi do `IF NOT EXISTS` khi đã trùng tên nhưng sai cấu trúc, chạy truy vấn đối chiếu chi tiết sau:
```sql
SELECT 
  i.relname AS index_name,
  ix.indisvalid,
  ix.indisready,
  ix.indisunique AS is_unique,
  pg_get_indexdef(ix.indexrelid) AS index_definition
FROM pg_index ix
JOIN pg_class i ON i.oid = ix.indexrelid
WHERE i.relname IN (
  'media_scoped_hash_idx',
  'media_unbound_active_hash_unique_idx',
  'media_variants_media_id_variant_type_unique_idx',
  'media_metadata_media_id_unique_idx'
);
```
**Yêu cầu xác minh & Manifest định nghĩa kỳ vọng**:
- **Trạng thái Index**: Cả hai cột **`indisvalid`** và **`indisready`** bắt buộc phải trả về **`true`**. Nếu một trong hai trường là `false`, chỉ mục đó bị coi là lỗi hoặc chưa sẵn sàng.
- **Cấu trúc Index**: Chuỗi `index_definition` nhận được từ catalog phải trùng khớp tuyệt đối cấu trúc với manifest sau:
  - `media_scoped_hash_idx`: `is_unique = false`. Definition chứa: `USING btree (uploaded_by, owner_type, owner_id, hash)`.
  - `media_unbound_active_hash_unique_idx`: `is_unique = true`. Definition chứa biểu thức predicate đầy đủ: `USING btree (uploaded_by, hash) WHERE ((owner_type IS NULL) AND (owner_id IS NULL) AND (deleted_at IS NULL) AND ((status)::text = ANY ((ARRAY['UPLOADING'::character varying, 'PROCESSING'::character varying, 'READY'::character varying])::text[])))`.
  - `media_variants_media_id_variant_type_unique_idx`: `is_unique = true`. Definition chứa: `USING btree (media_id, variant_type)`.
  - `media_metadata_media_id_unique_idx`: `is_unique = true`. Definition chứa: `USING btree (media_id)`.

*Hành động*: Nếu `indisvalid` hoặc `indisready` trả về `false`, hoặc chuỗi `index_definition` nhận được sai lệch so với manifest kỳ vọng, quản trị viên bắt buộc phải chạy lệnh DROP INDEX và khởi tạo lại concurrently:
`DROP INDEX CONCURRENTLY IF EXISTS "index_name";`
Sau đó chạy lại lệnh khởi tạo.

### Bước 3: Cập nhật Optimizer Statistics
Chạy lệnh `ANALYZE` ngay sau khi tạo index thành công để Postgres optimizer cập nhật số liệu thống kê cho bảng:
`ANALYZE media; ANALYZE media_variants; ANALYZE media_metadata;`

## 21. MIGRATION ROLLBACK POLICY
- **Chiến lược Forward-Fix (Ưu tiên số một)**: Trên production, nếu gặp lỗi deploy, không DROP cột hay phá hủy cấu trúc mà tiến hành sửa code nóng hoặc chạy migration vá (patch).
- **Rollback Destructive (Chỉ được phép khi có backup)**: Chỉ thực hiện hạ cấp (rollback DDL) bằng cách drop cột và index mới **trước khi code mới ghi dữ liệu** hoặc **sau khi đã có bản backup dữ liệu được xác nhận thành công**.
  - SQL Rollback:
    ```sql
    ALTER TABLE "media" DROP CONSTRAINT IF EXISTS "media_owner_pair_check";
    DROP INDEX CONCURRENTLY IF EXISTS "media_unbound_active_hash_unique_idx";
    DROP INDEX CONCURRENTLY IF EXISTS "media_scoped_hash_idx";
    DROP INDEX CONCURRENTLY IF EXISTS "media_variants_media_id_variant_type_unique_idx";
    DROP INDEX CONCURRENTLY IF EXISTS "media_metadata_media_id_unique_idx";
    ALTER TABLE "media" DROP COLUMN IF EXISTS "storage_provider";
    ALTER TABLE "media" DROP COLUMN IF EXISTS "alt_text";
    ALTER TABLE "media" DROP COLUMN IF EXISTS "caption";
    ```

## 24. SECURITY REVIEW OF SCHEMA DESIGN
- **Cross-owner Deduplication**: Scoped index cô lập theo `uploaded_by` ngăn chặn tuyệt đối việc người dùng khác đối khớp và tải lại ảnh của nhau.

- **Owner Consistency**: Check constraint `media_owner_pair_check` đảm bảo dữ liệu polymorphic không bao giờ bị lệch.
