## 1. Audit correction and final query shape

The initial closeout evidence was rejected because its hard-coded EXPLAIN SQL still used the obsolete global `nearby_ratings` CTE, returned zero rows, and did not prove the repository query then in production code. The benchmark harness has been corrected as follows:

- EXPLAIN SQL is captured and compiled from `DrizzleNearbyRepository.searchNearby`; the harness no longer maintains a duplicate SQL implementation.
- Every representative EXPLAIN uses `ANALYZE, BUFFERS, VERBOSE, SETTINGS` and must return at least one row.
- Evidence generation fails if the compiled repository query does not contain the current `LEFT JOIN LATERAL` shape or if a plan contains the obsolete `nearby_ratings` CTE.
- Old zero-row plans were removed and replaced with nine plans generated from the current repository.
- The final query remains one parameter-bound statement using `ST_DWithin`, `ST_Distance`, `UNION ALL`, stable keyset ordering and `limit + 1`.

The LATERAL rating aggregation allows each selected branch to use `reviews_owner_idx`; it does not introduce an N+1 application-query pattern.

---

## 2. Benchmark isolation and fail-closed behavior

The benchmark runner now requires `NEARBY_BENCHMARK_DATABASE_URL`. Seed, run and cleanup refuse to execute unless the database name ends with `_benchmark`. There is no fallback to the normal `DATABASE_URL`.

The runner also fails with a non-zero exit status when any of these conditions occurs:

- HTTP status is not 200 or the success envelope is inconsistent.
- A representative scenario unexpectedly returns no rows, or an empty scenario returns rows.
- Repository and HTTP result counts diverge.
- Exact page-two keyset or signed cursor cannot be produced.
- EXPLAIN generation fails or returns no representative rows.
- The 25 km database p95 gate fails.
- Concurrency success is below 100%.

Public type `place` is used for the tourist-place HTTP scenario. Cursor DB timing uses the repository's unrounded `rawDistanceMeters`, not the rounded public response value.

- 27 scenarios.
- 30 measured warm-cache samples per scenario after warmup.
- Nearest-rank p50, p95 and p99.
- Raw DB and HTTP samples saved in `benchmark-results.json`.
- Dataset cardinality is checked before timing: 1,200 places, 2,500 attractions, 6,000 businesses and 9,700 reviews.
- C8 and E4 are genuine successful empty-result scenarios.
- Performance target is the operational decision AD-NEARBY-006, not a public HTTP contract promise.

This measurement is local benchmark evidence. It must be revalidated after material data-growth, infrastructure or query-shape changes and is not represented as an internet/network latency guarantee.

## 6. Concurrency, security and architecture

- 10 concurrent 5 km requests: 100% HTTP 200; total batch duration 271.73 ms.
- All client-derived SQL values remain bound parameters.
- Public entity types are allowlisted.
- HMAC-SHA256 signed cursor is fingerprint-bound to coordinates, radius, entity types and filters.
- Raw distance precision is preserved in cursor/keyset comparisons.
- Latitude, longitude and cursor are redacted from request logs.
- Draft, inactive, deleted, invalid-region and invalid-business-type rows remain excluded.
- Controller contains no SQL; service contains no PostGIS; repository remains read-only.
- No OFFSET, total count, application N+1, queue or external search engine was introduced.
