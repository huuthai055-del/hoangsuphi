## 1. PROJECT ARCHITECTURE

---

### 1.1 Mục tiêu

Thiết kế một kiến trúc Backend có khả năng:

- Phục vụ tốt từ giai đoạn đầu (Hoàng Su Phì, ~10K users/tháng) đến giai đoạn trưởng thành (Toàn quốc, hàng triệu users/tháng) **mà không cần refactor kiến trúc**.
- Cho phép mỗi Phase sau **chỉ thêm module mới**, không sửa nền móng.
- Tách biệt rõ ràng: infrastructure, business logic, và presentation.
- Developer mới tham gia có thể hiểu cấu trúc và đóng góp trong vòng **một ngày**.

---

### 1.2 Thiết kế — Architectural Pattern

#### Lựa chọn: Layered Architecture + Ports & Adapters (Hexagonal) Hybrid

Dự án áp dụng kiến trúc **Layered** với nguyên tắc **Ports & Adapters** (Hexagonal Architecture) ở tầng Infrastructure.

```
┌─────────────────────────────────────────────────────────────┐
│                   PRESENTATION LAYER                        │
│         Hono Routes → Handler → DTO Validation              │
│         (HTTP In / Out — không chứa business logic)         │
├─────────────────────────────────────────────────────────────┤
│                   APPLICATION LAYER                         │
│         Use Cases / Services                                │
│         (Orchestrate Domain + Infrastructure calls)         │
│         (Pure TypeScript — không phụ thuộc framework)       │
├─────────────────────────────────────────────────────────────┤
│                     DOMAIN LAYER                            │
│         Entities | Value Objects | Domain Events            │
│         Repository Interfaces (Ports)                       │
│         (Không phụ thuộc bất kỳ framework hay DB nào)      │
├─────────────────────────────────────────────────────────────┤
│                 INFRASTRUCTURE LAYER                        │
│         Drizzle ORM | Redis | S3 | Typesense | Email        │
│         (Adapters — thực thi Ports của Domain)              │
└─────────────────────────────────────────────────────────────┘
```

#### Nguyên tắc phụ thuộc (Dependency Rule)

```
Presentation → Application → Domain ← Infrastructure
```

> **Tuyệt đối không vi phạm:** Infrastructure KHÔNG ĐƯỢC import từ Application/Domain layer. Domain KHÔNG ĐƯỢC import từ bất kỳ đâu bên ngoài.

```
✅ Đúng:   Route → Service → Repository Interface ← Repository Implementation (Drizzle)
❌ Sai:    Domain Entity → import { db } from '../lib/db'
❌ Sai:    Service → import { sql } from 'drizzle-orm'
```

---

### 1.3 Lý do lựa chọn

| Yếu tố | Lý do |
|:---|:---|
| **Layered** | Đơn giản hơn Pure DDD — phù hợp team size và timeline |
| **Ports & Adapters** | Cho phép swap infrastructure (Drizzle → Prisma, Redis → Memcached) mà không sửa domain |
| **Không Pure DDD** | Full DDD (Aggregate Root, Domain Event Bus...) quá phức tạp cho giai đoạn bootstrap — sẽ adopt dần ở Phase 4+ |
| **Module-based** | Mỗi bounded context (businesses, articles, regions...) là một module độc lập → scale team dễ |

---

### 1.4 Ưu điểm

- **Testability:** Domain và Application layer thuần TypeScript → unit test không cần mock DB hay Hono
- **Flexibility:** Swap bất kỳ adapter nào (DB, Cache, Storage) mà không ảnh hưởng business logic
- **Onboarding:** Developer mới chỉ cần đọc module mình phụ trách — không cần hiểu toàn bộ system
- **Parallel Development:** Các module độc lập → nhiều developer làm song song không conflict
- **Phase Expansion:** Thêm module mới = thêm folder mới, không sửa code cũ

---

### 1.5 Nhược điểm

- **Boilerplate:** Repository interface + Implementation tốn thêm ~30% code so với viết thẳng vào service
- **Over-engineering cho MVP:** Nếu scope không mở rộng như kế hoạch, kiến trúc này hơi phức tạp

---

### 1.6 Các lựa chọn khác đã xem xét

| Pattern | Mô tả |
|:---|:---|
| **Flat MVC** | Route → Controller → Model. Đơn giản nhưng không scale |
| **Pure DDD** | Aggregate Root, Domain Event Bus, CQRS. Quá phức tạp cho Phase 2 |
| **CQRS + Event Sourcing** | Phù hợp khi traffic > 10M req/day. Quá sớm |
| **Microservices** | Không phù hợp — team nhỏ, overhead devops quá lớn |

---

### 1.7 Vì sao không chọn

- **Flat MVC:** Khi module tăng lên 15+ (Phase 3), controller sẽ bloat, logic leak sang model. Không refactor được không đau.
- **Microservices:** Chi phí vận hành (service mesh, distributed tracing, eventual consistency) không tương xứng với lợi ích ở scale hiện tại. Modular Monolith với clear boundaries dễ extract thành microservice sau này.
- **Pure DDD:** Overkill cho Phase 2. Sẽ adopt incrementally từ Phase 3-4.

---

### 1.8 Khả năng mở rộng

```
Phase 2-3:  Modular Monolith (hiện tại)
Phase 4-5:  Thêm CQRS (tách read/write model cho Article, Business)
Phase 6-7:  Extract Search Service, Media Service thành microservice nếu cần
Phase 8+:   Full Microservices nếu scale đòi hỏi
```

Kiến trúc hiện tại được thiết kế để **extract module thành microservice** dễ dàng vì:
- Mỗi module có repository interface riêng → dễ swap sang gRPC/HTTP call
- Domain layer thuần TypeScript → move sang service mới không phụ thuộc framework

---

### 1.9 Best Practices áp dụng

- **Single Responsibility:** Mỗi class/function chỉ làm một việc
- **Dependency Inversion:** Depend on abstractions (interfaces), not concretions
- **Interface Segregation:** Repository interface nhỏ, focused — không dump tất cả methods vào 1 interface
- **Fail Fast:** Validate input ở boundary (Presentation layer), không validate lại ở Domain
- **Pure Functions:** Ưu tiên pure functions trong Domain và Application layer

## 2. FOLDER STRUCTURE

---

### 2.1 Mục tiêu

Cấu trúc thư mục phải:
- Phản ánh **kiến trúc**, không phản ánh file type
- Developer đọc folder structure là hiểu được bounded contexts
- Không có "utils dump" hay "helpers" folder vô tổ chức

---

### 2.3 Quy ước đặt tên file

```
[module].[layer].ts

Ví dụ:
  auth.route.ts          ← Presentation (Hono route definition + handler)
  auth.service.ts        ← Application (business logic / use cases)
  auth.repository.ts     ← Infrastructure (database + redis access)
  auth.dto.ts            ← Shared within module (Zod in/out schemas)
  auth.errors.ts         ← Module-specific custom error classes
```

---

### 2.4 Module Structure Convention

Mỗi module trong `modules/` phải tuân theo cấu trúc sau:

```
modules/[name]/
├── [name].route.ts      ← REQUIRED: Hono route definitions + inline handler
├── [name].service.ts    ← REQUIRED: Application/business logic
├── [name].repository.ts ← REQUIRED: Data access layer (Drizzle + Redis)
├── [name].dto.ts        ← REQUIRED: Zod request/response schemas
└── [name].errors.ts     ← OPTIONAL: Module-specific custom errors
```

> **Quy tắc bắt buộc:** KHÔNG tạo `controllers/`, `models/`, `utils/` rải rác — tất cả phải thuộc module.

---

### 2.5 Dependency Rules (Bắt buộc — sẽ enforce bằng linting)

```typescript
// ✅ Allowed:
// index.ts → app.ts → middleware/* → modules/*
// modules/*/  → common/* → lib/*
// modules/auth/auth.service.ts → lib/database/client.ts (qua repository)
// modules/auth/auth.repository.ts → lib/database/client.ts ✅
// modules/auth/auth.repository.ts → lib/redis/client.ts ✅

// ❌ Forbidden:
// lib/* → modules/*          (infrastructure không biết domain)
// common/* → modules/*       (common không biết module cụ thể)
// modules/auth/* → modules/businesses/*   (modules không import nhau trực tiếp)
// modules/*/auth.service.ts → lib/database/client.ts trực tiếp (phải qua repository)
```

> **Modules giao tiếp nhau** thông qua: Application Events (Phase 4+) hoặc Service injection — KHÔNG import chéo trực tiếp.

---

### 2.6 TypeScript Path Aliases

```jsonc
// tsconfig.json
{
  "compilerOptions": {
    "paths": {
      "@/config/*":     ["./src/config/*"],
      "@/lib/*":        ["./src/lib/*"],
      "@/common/*":     ["./src/common/*"],
      "@/middleware/*": ["./src/middleware/*"],
      "@/modules/*":    ["./src/modules/*"]
    }
  }
}
```

```typescript
// Sử dụng:
import { env } from '@/config/env'
import { db } from '@/lib/database/client'
import { AppError } from '@/common/errors/app.error'
```

---

### 2.7 Khả năng mở rộng

```
Phase 3:  Thêm modules/businesses, modules/articles... → chỉ tạo folder mới
Phase 4:  Thêm events/ trong mỗi module → Domain Events
Phase 5:  Thêm apps/frontend → workspace sẵn sàng
Phase 6+: Extract module thành microservice → move folder ra apps/ mới
```

---

### 2.8 Best Practices

- **Barrel exports:** Mỗi module export qua `index.ts` (public API) — internal files không expose ra ngoài
- **Absolute imports:** TypeScript path aliases tránh `../../../` hell
- **No circular dependencies:** Enforce bằng `eslint-plugin-import` rule `import/no-cycle`
- **Co-location:** Test file mirror src structure trong `tests/`
