## 1. MỤC TIÊU

Thiết kế giao diện API RESTful hoàn chỉnh cho **Identity Module** (phiên bản `v1`) nhằm:
- Đặc tả rõ ràng các endpoints, phương thức truyền tải HTTP, cấu trúc yêu cầu (Request Body / Headers) và phản hồi (Response Payload).
- Đảm bảo toàn bộ phản hồi lỗi tuân thủ nghiêm ngặt chuẩn **RFC 7807 (Problem Details)** và bảng mã lỗi tập trung [error-codes.md](file:///c:/Users/tony/Desktop/youtube/hoangsuphi/backend/docs/error-codes.md).
- Thiết lập cơ chế truyền tải token an toàn qua **HTTP Cookies** bảo mật cao (HttpOnly, Secure, SameSite=Strict).
- Xác định rõ phân quyền (Permissions/RBAC) cần thiết để truy cập từng endpoint.
- Đảm bảo tính **Idempotency** đối với các thao tác đăng xuất (Logout) và xoay vòng token (Refresh).
- Toàn bộ các endpoint của Identity Module có tiền tố là `/api/v1/auth/` hoặc `/api/v1/users/`.

---

## 2. THIẾT KẾ & KIẾN TRÚC API

### 2.1 Tổng quan Endpoints

| HTTP Method | Path | Xác thực? | Quyền hạn (Permissions) | Mô tả |
|:---|:---|:---:|:---:|:---|
| **POST** | `/api/v1/auth/login` | ❌ Không | Public | Đăng nhập tài khoản, thiết lập Session mới |
| **POST** | `/api/v1/auth/refresh` | ❌ Không | Public (Cần Cookie) | Dùng Refresh Token lấy Access Token mới |
| **POST** | `/api/v1/auth/logout` |  Có | Bất kỳ ai đã login | Đăng xuất thiết bị hiện tại (hủy session) |
| **GET** | `/api/v1/users/me` |  Có | `user:read` | Lấy thông tin hồ sơ của user đăng nhập hiện tại |
| **PATCH** | `/api/v1/users/me` |  Có | `user:write` | Cập nhật một phần thông tin hồ sơ cá nhân |

---

### 2.2 Chi tiết thiết kế từng Endpoint

#### 1. POST `/api/v1/auth/login`

##### Request Headers
```http
Content-Type: application/json
```

##### Request Body (Zod validated)
```json
{
  "email": "user@hoangsuphi.vn",
  "password": "strong_password_123",
  "deviceId": "c8b35f28-090c-4e86-a212-32a2c07466fa" // Fingerprint định danh thiết bị
}
```

##### Response Headers (Thành công - 200 OK)
```http
Content-Type: application/json
Set-Cookie: hsp_refresh_token=rt_jwt_string; Path=/api/v1/auth; HttpOnly; Secure; SameSite=Strict; Max-Age=2592000
```
> [!NOTE]
> Refresh Token được gửi dưới dạng **HttpOnly Cookie** bảo mật cao để chống lại các cuộc tấn công XSS chiếm đoạt Token trên trình duyệt. Cookie này chỉ được gửi lên trong phạm vi router `/api/v1/auth` (chủ yếu là endpoint `/refresh`).

##### Response Body (Chuẩn hóa response format `{ data, meta }`)
```json
{
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1NiIsIn...", // Hạn dùng 15 phút
    "expiresIn": 900,                           // 15 * 60 giây
    "tokenType": "Bearer"
  }
}
```

##### Lỗi có thể xảy ra (RFC 7807)
- **AUTH_001 (Unauthenticated):** Mật khẩu sai hoặc email không tồn tại.
- **VAL_001 (Validation Failed):** Định dạng email sai, thiếu password hoặc deviceId.

#### 2. POST `/api/v1/auth/refresh`

Lấy Access Token mới. Yêu cầu Cookie `hsp_refresh_token` hợp lệ.

##### Request Headers
```http
Cookie: hsp_refresh_token=rt_jwt_string
```

##### Response Headers (Thành công - 200 OK)
```http
Content-Type: application/json
```

##### Response Body (Chuẩn hóa response format `{ data, meta }`)
```json
{
  "data": {
    "accessToken": "new_ey...accessToken",
    "expiresIn": 900,
    "tokenType": "Bearer"
  }
}
```


##### Lỗi có thể xảy ra (401 Unauthorized)
Nếu Refresh Token hết hạn hoặc không tồn tại trong DB:
```json
{
  "type": "https://hoangsuphi.vn/errors/unauthenticated",
  "title": "Session Expired",
  "status": 401,
  "code": "AUTH_003",
  "detail": "Session has expired or was revoked.",
  "instance": "/api/v1/auth/refresh",
  "traceId": "7e7d8c6b...",
  "retryable": false
}
```

---

#### 3. POST `/api/v1/auth/logout`

Hủy phiên đăng nhập của thiết bị hiện hữu.

##### Request Headers
```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsIn...
Cookie: hsp_refresh_token=rt_jwt_string
```

##### Response Body (200 OK - Chuẩn hóa response format `{ data, meta }`)
```json
{
  "data": {
    "success": true,
    "message": "Successfully logged out from current device."
  }
}
```
> [!NOTE]
> Cookie `hsp_refresh_token` sẽ bị set lại thời gian sống thành quá khứ (`Max-Age=0`) để trình duyệt tự động xóa.

##### Idempotency
Endpoint này có tính lũy đẳng (Idempotency). Gọi liên tục 2 lần đăng xuất vẫn trả về `200 OK` (lần 2 không làm gì vì session đã bị revoke).

## 4. DEPENDENCY & LUỒNG DỮ LIỆU

```
Client JSON/Cookies -> Validation Middleware -> Auth Route Handler -> Domain Entity -> Database Persistence
```

1. **Headers Validation:** Tự động bắt Authorization Header (`Bearer token`) thông qua `authenticate` middleware của Foundation (02.09).
2. **DTO Parsing:** Chạy qua validate middleware của Zod, ép kiểu dữ liệu đầu vào.
3. **Data Sanitization:** Trả dữ liệu sạch cho Service để tương tác với Domain.

---

## 5. BEST PRACTICES

- **Secure Cookies Attributes:** Bắt buộc áp dụng `HttpOnly` (chống XSS đọc token), `Secure` (chỉ gửi qua HTTPS), và `SameSite=Strict` (chống tấn công CSRF) cho Cookie Refresh Token.
- **Lũy đẳng cho Logout:** Logout là hành động thay đổi trạng thái an toàn. Nên đảm bảo nếu gọi nhiều lần thì trạng thái kết quả của tài khoản vẫn là "Đã logout" và trả về HTTP `200` để tránh UI frontend bị crash.

---

## 6. KHẢ NĂNG MỞ RỘNG

- **API Versioning:** Cấu trúc `/api/v1/` giúp sau này phát hành `/api/v2/auth/` dùng cơ chế xác thực sinh trắc học (WebAuthn/FIDO2) hoặc OAuth3 mà không gây ngắt quãng client cũ đang chạy v1.

---

## 7. SECURITY

- **Chống brute-force đăng nhập:** Giới hạn tốc độ login `/auth/login` tối đa **10 requests/phút** trên mỗi IP address thông qua Rate Limiter (đã thiết lập trong `app.config.ts`).
- **CSRF Protection:** Sử dụng `SameSite=Strict` và không lưu trữ Access Token trong Cookie (chỉ lưu Refresh Token). Access Token chỉ tồn tại trong bộ nhớ RAM của JS Client.

---

## 8. PERFORMANCE

- **Cookie Path scoping:** Đặt thuộc tính `Path=/api/v1/auth` cho Refresh Token cookie giúp trình duyệt KHÔNG gửi cookie này lên ở các trang tĩnh, trang blog hoặc homestay lists, tiết kiệm đáng kể băng thông tải.
- **Sub-10ms validation:** Validation schema của login gọn nhẹ, loại bỏ các ký tự lạ nhanh chóng bằng Zod validation.

---

## 9. CÁC LỰA CHỌN KHÁC ĐÃ XEM XÉT

| Phương án | Vấn đề |
|:---|:---|
| **Lưu Refresh Token trong LocalStorage** | Rất dễ bị tấn công XSS. Một thư viện bên thứ 3 bị nhiễm mã độc (như package npm bị hack) có thể dễ dàng đọc `localStorage.getItem('refreshToken')` và gửi về server hacker. |
| **Gửi cả Access Token trong Cookie** | Gây nguy cơ bị tấn công CSRF trừ khi thiết lập double-submit cookie token rất phức tạp. |

---

## 10. VÌ SAO KHÔNG CHỌN

- **LocalStorage cho Refresh Token:** Bảo mật là ưu tiên hàng đầu của IAM module. Tránh LocalStorage cho token dài hạn là tiêu chuẩn an toàn bắt buộc của OWASP (ASVS v4.0).
- **Access Token trong Cookie:** Do Access Token được gửi lên ở mọi API request, việc đưa vào cookie sẽ tăng nguy cơ CSRF và làm tăng độ phức tạp của CORS configuration trên các sub-domains khác nhau.
