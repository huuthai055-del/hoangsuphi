## 2. Final Architecture

Luồng production được xác minh:

```text
POST /api/v1/media/upload
→ authentication + permission + multipart/body limit
→ MediaController (thin HTTP boundary)
→ MediaIngestionService
→ magic-byte/MIME/size/pixel/decode validation
→ SharpImageProcessor
→ IMediaStorage → CloudinaryStorageAdapter
→ IMediaRepository → PostgreSQL
```

- Không có Media module thứ hai.
- Controller không import Sharp hoặc Cloudinary SDK.
- Application service chỉ phụ thuộc storage port/resolver, không import Cloudinary SDK.
- Chỉ `cloudinary-storage.adapter.ts` import Cloudinary SDK trong production source.
- Sharp/Cloudinary I/O chạy ngoài transaction. Transaction cuối chỉ ghi metadata, variants và READY.
- Không thêm Queue, BullMQ, worker, event bus, microservice hoặc external search engine.
- LOCAL chỉ phục vụ legacy/development/test. Staging/production thiếu Cloudinary configuration sẽ fail fast khi parse environment.

## 3. Lifecycle

Lifecycle duy nhất:

```text
UPLOADING → PROCESSING → READY
     └───────────────→ FAILED
PROCESSING ──────────→ FAILED
READY/FAILED ────────→ DELETED (soft delete)
```

- Direct `UPLOADING → READY` đã bị loại bỏ.
- Conditional repository updates chặn stale state overwrite.
- READY chỉ được ghi sau processing và provider uploads hoàn tất.
- Metadata + variants + READY được commit atomically.
- Lỗi processing/provider/finalization chuyển bản ghi sang FAILED khi phù hợp.
- Lỗi đọc lại sau khi finalization thành công không xóa asset và không đổi READY thành FAILED.
- Public GET chỉ trả Media READY; FAILED/PROCESSING/UPLOADING/DELETED không được publish.

## 4. Validation Policy

- Public ingestion chỉ chấp nhận JPEG, PNG và WebP.
- GIF, SVG, video, document và payload không phải ảnh bị từ chối.
- Filename chỉ là metadata, được sanitize, chặn traversal và giới hạn theo cột 255 ký tự.
- MIME khai báo phải khớp magic bytes; client MIME không được tin riêng lẻ.
- Sharp phải decode được input; ảnh corrupt/truncated bị từ chối, không sinh fallback giả.
- Raw file limit: 10 MiB. HTTP ingress có khoảng đệm multipart nhưng service vẫn áp dụng limit 10 MiB chính xác.
- Kích thước tối đa mỗi chiều: 12.000 px; tổng pixels tối đa: 40.000.000.
- Sharp `limitInputPixels` bảo vệ decode path khỏi input vượt giới hạn.
- Một file mỗi request; unknown/owner-binding multipart fields bị strict validation từ chối.

## 5. Sharp Processing & Variant Contract

- Sanitized master: WebP quality 85, giữ kích thước auto-oriented thực tế.
- `thumbnail`: fit-inside 320×320, WebP quality 80, không upscale.
- `medium`: fit-inside 768×768, WebP quality 80, không upscale.
- `large`: fit-inside 1600×1600, WebP quality 80, không upscale.
- Output đã được decode lại bằng Sharp trong tests.
- Width, height và byte-size được lấy từ output thực, không từ client.
- Auto-orientation được áp dụng trước resize; test regression bao phủ orientation làm đổi width/height.

## 6. EXIF & Privacy Policy

- Không gọi `.withMetadata()` hoặc `.keepMetadata()` trên public outputs.
- Sanitized master và variants không giữ EXIF, GPS, XMP hoặc IPTC.
- PostgreSQL metadata chỉ lưu allowlisted technical values (`width`, `height`, `mimeType`, `fileSize`, `processedAt`).
- Camera, model, orientation gốc và GPS không được persistence/public response.

## 7. Storage-provider Design

- Cloudinary nằm sau `IMediaStorage`; logical key/public ID được tạo từ server-owned media ID và variant name.
- Upload dùng stream, không base64 data URI.
- Download có timeout 10 giây, Content-Length fast reject và stream byte cap 50 MiB.
- Upload/delete/exists có operation timeout; provider errors được chuyển thành safe domain error.
- Delete-not-found là idempotent success.
- Production configuration names: `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` (không ghi giá trị).
- Test configuration names: `CLOUDINARY_TEST_CLOUD_NAME`, `CLOUDINARY_TEST_API_KEY`, `CLOUDINARY_TEST_API_SECRET` (không fallback sang production credentials).

## 8. Transaction Boundaries

1. Ghi Media UPLOADING và commit.
2. Conditional transition sang PROCESSING và commit.
3. Validate/decode/process/upload master và variants ngoài DB transaction.
4. Transaction ngắn cuối: upsert metadata, upsert variants, conditional PROCESSING → READY.
5. Khi bước 3/4 lỗi: compensation storage ngoài transaction, sau đó conditional FAILED operation độc lập.

Không có external provider call bên trong transaction.

## 9. Compensation Matrix

| Failure | Storage action | DB action | Client result |
| :--- | :--- | :--- | :--- |
| Validation/Sharp trước upload | Không có asset để xóa | Không tạo hoặc chuyển FAILED theo stage | Safe validation/system error |
| Master/variant upload lỗi | Xóa đúng mọi key đã đăng ký cho attempt | Chuyển FAILED | Safe storage error |
| Final DB transaction lỗi | Xóa master + mọi variant của attempt | Transaction rollback; chuyển FAILED độc lập | Safe system error |
| Cleanup delete lỗi | Tiếp tục best-effort các key còn lại; log safe class/stage | Giữ FAILED/retryable state | Lỗi gốc không bị che |
| Post-finalize read lỗi | Không cleanup | Giữ READY | Safe system error |
| Client abort trước finalize | Cleanup các key của attempt | Chuyển FAILED | Abort/error; không false success |

## 10. Deduplication & Ownership

- Dedup production dùng `(uploadedBy, ownerType, ownerId, hash)`; không dùng global hash-only path.
- Upload mới lấy uploader từ trusted auth context và bắt đầu unbound (`ownerType/ownerId = null`).
- Public multipart DTO không cho client truyền owner UUID.
- READY cùng scope trả 200 và `meta.deduplicated = true`.
- UPLOADING/PROCESSING cùng scope trả conflict; FAILED/DELETED cho phép attempt mới.
- Different uploader hoặc owner không nhận Media của nhau.
- Partial unique index bảo vệ concurrent active unbound duplicates ở database.

## 11. Public API & Error Contract

- Success envelope: `{ data, meta, error: null }`.
- New upload trả 201; READY dedup hit trả 200.
- Mapper explicit chỉ trả public ID/name/url/type/dimensions/size/alt/caption/variants.
- Không public `storageKey`, provider public ID, hash, uploader, owner internals, raw lifecycle/failure state, cleanup state, provider response, EXIF/GPS, SQL hoặc stack trace.
- Failure dùng RFC 7807 conventions và project error codes.
- Không auth: 401; thiếu permission: 403; invalid multipart/validation: 400; concurrent/in-flight duplicate: 409; safe infrastructure failure: 500.

## 13. Retention & Operational Purge

- DELETE public là soft delete.
- `media:purge` là command scheduler ngoài request process, retention mặc định 30 ngày, batch tối đa 100 (hard cap 500).
- Candidate + variants được đọc set-based bằng hai query cố định; không N+1.
- Storage keys được xóa tuần tự; DB chỉ hard-delete khi toàn bộ provider cleanup thành công.
- Cleanup lỗi giữ row DELETED để lần scheduler sau retry.
- PostgreSQL integration xác minh candidate/variant mapping và conditional hard delete.
- Production nên chạy command hằng ngày; không dùng queue/worker in-process.
