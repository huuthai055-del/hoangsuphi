## 1. MỤC TIÊU

Thiết kế các đối tượng truyền tải dữ liệu (DTO - Data Transfer Objects) và các quy tắc kiểm tra tính hợp lệ dữ liệu đầu vào (Input Validation Schemas) cho **Identity Module** nhằm:
- Bảo vệ biên giới API khỏi dữ liệu rác, độc hại hoặc thiếu cấu trúc bằng công cụ validate mạnh mẽ **Zod**.
- Thống nhất các quy tắc validate đơn giản, hiệu quả cho MVP cấp huyện (như định dạng email, độ dài mật khẩu tối thiểu, trường dữ liệu profile).
- Tự động hóa việc loại bỏ các tham số thừa (Mass Assignment prevention) trước khi dữ liệu đi vào Service Layer.
- Đồng bộ hóa định dạng thông báo lỗi validate theo chuẩn **RFC 7807 (Problem Details)** thông qua danh sách `invalidParams` chi tiết.

---

## 2. THIẾT KẾ & KIẾN TRÚC DTO

```
Client Payload (JSON) ──> [Zod Validation Middleware] ──> Clean DTO Object (TypeScript Typed)
                                                                 │
                                                                 ▼ (Passed to)
                                                           Service Layer
```

Các DTO được chia làm hai loại chính:
1. **Request DTOs:** Nhận dữ liệu đầu vào từ HTTP request, được validate chặt chẽ ở lớp Presentation.
2. **Response DTOs:** Định cấu trúc dữ liệu trả về cho Client, đảm bảo không rò rỉ dữ liệu nhạy cảm (như password hashes).

---

### 2.1 Đặc tả Zod Schemas & DTOs

Các DTO này nằm trong tệp `apps/backend/src/modules/auth/dto/auth.dto.ts` và `apps/backend/src/modules/users/dto/users.dto.ts`.

#### 1. Authentication Request Schemas & DTOs (`auth.dto.ts`)

##### A. Login DTO
```typescript
import { z } from 'zod'

export const LoginRequestSchema = z.object({
  email: z
    .string({ required_error: 'Email is required' })
    .email('Invalid email address')
    .trim()
    .toLowerCase(),
  password: z
    .string({ required_error: 'Password is required' })
    .min(8, 'Password must be at least 8 characters')
    .max(100, 'Password must not exceed 100 characters'),
  deviceId: z
    .string({ required_error: 'Device ID is required' })
    .uuid('Device ID must be a valid UUID')
}).strict() // Ngăn chặn truyền thêm dữ liệu rác

export type LoginRequestDto = z.infer<typeof LoginRequestSchema>
```

##### B. Token Response DTO
```typescript
export interface TokenResponseDto {
  accessToken: string
  refreshToken: string
  expiresIn: number // giây (ví dụ: 900)
}
```

#### 2. Users Profile Schemas & DTOs (`users.dto.ts`)

##### A. Update Profile DTO
```typescript
export const UpdateProfileSchema = z.object({
  firstName: z
    .string()
    .trim()
    .min(1, 'First name cannot be empty')
    .max(50, 'First name must not exceed 50 characters')
    .optional(),
  lastName: z
    .string()
    .trim()
    .min(1, 'Last name cannot be empty')
    .max(50, 'Last name must not exceed 50 characters')
    .optional(),
  avatarUrl: z
    .string()
    .url('Avatar URL must be a valid URL')
    .max(255, 'Avatar URL must not exceed 255 characters')
    .nullable()
    .optional(),
  phoneNumber: z
    .string()
    .trim()
    .regex(/^(0|\+84)[3|5|7|8|9][0-9]{8}$/, 'Invalid Vietnamese phone number format')
    .optional()
    .nullable(),
  bio: z
    .string()
    .trim()
    .max(200, 'Bio must not exceed 200 characters')
    .optional()
    .nullable()
}).strict()

export type UpdateProfileDto = z.infer<typeof UpdateProfileSchema>
```

##### B. User Profile Response DTO
```typescript
export interface UserProfileResponseDto {

    firstName: string

    bio: string | null
  }
  lastLoginAt: Date | null
}
```

## 3. LUỒNG DỮ LIỆU & XỬ LÝ LỖI VALIDATION (RFC 7807)

Khi validator phát hiện lỗi (ví dụ: gửi thiếu `deviceId` và định dạng `email` sai):

### 1. Luồng chạy
```
Client Request ──> Hono Zod Validator Middleware ──> (Lỗi ZodError) ──> Mapper ──> Response RFC 7807 400 Bad Request
```

### 2. Định dạng Response Lỗi Validation (RFC 7807)
Mã lỗi chung cho lỗi validate biểu mẫu là `VAL_001` (định nghĩa tại `error-codes.md`).

```json
{
  "type": "https://hoangsuphi.vn/errors/validation-failed",
  "title": "Validation Failed",
  "status": 400,
  "code": "VAL_001",
  "detail": "One or more request parameters are invalid.",
  "instance": "/api/v1/auth/login",
  "traceId": "9f8e7d6c5b4a...",
  "invalidParams": [
    {
      "name": "email",
      "reason": "Invalid email address"
    },
    {
      "name": "deviceId",
      "reason": "Device ID must be a valid UUID"
    }
  ],
  "retryable": false
}
```

## 5. BEST PRACTICES

- **Strict Mode (`.strict()`):** Bắt buộc bật strict mode cho toàn bộ request Zod schemas để tự động reject các fields lạ gửi lên từ hacker, chặn đứng lỗ hổng Mass Assignment.
- **Normalization (Chuẩn hóa):** Tận dụng `.trim()` và `.toLowerCase()` trực tiếp trong Schema của Zod để chuẩn hóa dữ liệu email, loại bỏ khoảng trắng dư thừa trước khi lưu DB.
- **Tách biệt DTO và Domain Entity:** Không bao giờ pass trực tiếp đối tượng Zod parse result hay DTO vào Domain Entity constructor. Luôn map qua constructor tường minh hoặc mapper.

---

## 6. KHẢ NĂNG MỞ RỘNG (FUTURE ENHANCEMENTS)

- **Password Complexity Rules:** Ở giai đoạn MVP, mật khẩu chỉ cần tối thiểu 8 ký tự. Sau này khi nâng cấp quy mô toàn quốc, ta chỉ cần sửa schema Zod password (thêm `.regex()` kiểm tra chữ hoa, chữ số, ký tự đặc biệt) mà không ảnh hưởng tới logic của controller hay services.

---

## 7. SECURITY

- **Chặn Mass Assignment:** Việc dùng `.strict()` trên Zod đảm bảo hacker không thể chèn thêm các trường nhạy cảm như `"role": "admin"` hoặc `"status": "ACTIVE"` vào body API cập nhật profile hoặc đăng ký.
- **Regex Phone Number chuẩn Việt Nam:** Kiểm soát định dạng số điện thoại chuẩn viễn thông Việt Nam giúp giảm thiểu rác và tăng chất lượng dữ liệu để sau này SMS OTP.
