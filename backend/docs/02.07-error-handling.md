## 1. GLOBAL ERROR HANDLING & EXCEPTION HIERARCHY

---

### 1.1 Mục tiêu

- **Tính nhất quán của phản hồi lỗi (Response Consistency):** Đảm bảo mọi lỗi phát sinh từ bất kỳ đâu (API, Validation, DB, Service) đều trả về client với cùng một định dạng JSON thống nhất.
- **Phân cấp lỗi rõ ràng (Clear Exception Hierarchy):** Sử dụng các custom classes kế thừa từ `AppError` để tầng trình diễn (Presentation) có thể tự động map sang mã trạng thái HTTP thích hợp mà không cần viết các câu lệnh `if-else` phức tạp.
- **Bảo mật môi trường sản xuất (Production Safety):** Ẩn hoàn toàn chi tiết lỗi hệ thống (stack trace, raw DB error) đối với client ở Production để tránh lộ lỗ hổng, nhưng vẫn lưu đầy đủ thông tin chi tiết kèm `requestId` trong hệ thống log nội bộ.
- **Phân loại mức độ ghi log (Log Level Hierarchy):** 
  - Các lỗi do client (4xx) được log ở mức `warn` hoặc `info` (tránh spam cảnh báo đỏ không đáng có).
  - Các lỗi do server (5xx) được log ở mức `error` hoặc `fatal` kèm đầy đủ stack trace để kích hoạt cảnh báo hệ thống (Sentry/Alerting).

---

### 1.2 Thiết kế

Chúng ta xây dựng cấu trúc lỗi dựa trên định dạng phản hồi chuẩn hóa **RFC 7807 (Problem Details for HTTP APIs)** - chuẩn công nghiệp cho các API RESTful chuyên nghiệp.

#### 1. Cấu trúc Response Lỗi chuẩn (RFC 7807)

Mọi phản hồi lỗi sẽ trả về Content-Type `application/problem+json` với schema sau:

```json
{
  "type": "https://hoangsuphi.vn/errors/validation-error", // URI định nghĩa loại lỗi
  "title": "Validation Failed",                             // Tiêu đề lỗi ngắn gọn
  "status": 400,                                             // HTTP Status Code
  "code": "VALIDATION_FAILED",                               // Mã lỗi nội bộ (Internal Error Code)
  "detail": "The request body contains invalid parameters.", // Mô tả chi tiết lỗi
  "instance": "/api/v1/auth/login",                          // Endpoint phát sinh lỗi
  "invalidParams": [                                         // Chi tiết lỗi validate (nếu có)
    {
      "name": "email",
      "reason": "Invalid email address format"
    }
  ]
}
```

#### 2. Base Exception: `apps/backend/src/common/errors/app.error.ts`

```typescript
export interface ErrorDetails {
  [key: string]: any
}

export abstract class AppError extends Error {
  public abstract readonly statusCode: number
  public abstract readonly errorCode: string // Internal catalog code, ví dụ: 'AUTH_001', 'VAL_001'
  public readonly retryable: boolean = false

  constructor(
    message: string,
    public readonly details?: ErrorDetails,
    options?: { cause?: Error; retryable?: boolean; typeUri?: string }
  ) {
    super(message, { cause: options?.cause })
    this.name = this.constructor.name
    this.retryable = options?.retryable ?? false
    // Đảm bảo stack trace chính xác trong V8 engine (Bun tương thích)
    Error.captureStackTrace(this, this.constructor)
  }
}
```

#### 4. Global Error Middleware: `apps/backend/src/middleware/error-handler.middleware.ts`

Bắt và chuẩn hóa toàn bộ lỗi trong Hono.

```typescript
import type { ErrorHandler } from 'hono'
import { isProd } from '@/config/env'
import { logger } from '@/lib/logger'
import { AppError } from '@/common/errors/app.error'

export const errorHandlerMiddleware = (): ErrorHandler => {
  return async (err, c) => {
    const instance = c.req.path
    // Trích xuất traceId (requestId) đã sinh ra ở Logger middleware để phản hồi cho client
    const traceId = c.res.headers.get('x-request-id') || 'unknown'
    
    // 1. Trường hợp lỗi là AppError được định nghĩa sẵn
    if (err instanceof AppError) {
      const isClientError = err.statusCode < 500
      const logPayload = {
        statusCode: err.statusCode,
        errorCode: err.errorCode,
        detail: err.message,
        details: err.details,
        instance,
        traceId,
        cause: err.cause ? { message: err.cause.message, stack: err.cause.stack } : undefined,
      }

      if (isClientError) {
        logger.warn(logPayload, `⚠️ Client Error: ${err.message}`)
      } else {
        logger.error({ ...logPayload, stack: err.stack }, `❌ Server Error: ${err.message}`)
      }

      c.res.headers.set('Content-Type', 'application/problem+json')
      return c.json(
        {
          type: err.typeUri,
          title: err.name.replace(/Error$/, ' Failed'),
          status: err.statusCode,
          code: err.errorCode,
          detail: err.message,
          instance,
          traceId,
          retryable: err.retryable,
          ...(err.details ? { invalidParams: err.details } : {}),
        },
        err.statusCode as any
      )
    }

    // 2. Trường hợp lỗi validate mặc định của Zod
    if (err.name === 'ZodError') {
      logger.warn({ err: err.message, instance, traceId }, '⚠️ Unhandled Zod validation error')
      c.res.headers.set('Content-Type', 'application/problem+json')
      return c.json(
        {
          type: 'https://hoangsuphi.vn/errors/validation-failed',
          title: 'Validation Failed',
          status: 400,
          code: 'VAL_001',
          detail: 'Invalid input parameters',
          instance,
          traceId,
          retryable: false,
        },
        400
      )
    }

    // 3. Trường hợp unhandled Native Error (Lỗi hệ thống bất ngờ - 500)
    logger.error({ err: err.message, stack: err.stack, instance, traceId }, '🚨 Unhandled System Exception')

    c.res.headers.set('Content-Type', 'application/problem+json')
    
    const responseDetail = isProd 
      ? 'An unexpected system error occurred. Please contact system administrator.' 
      : err.message

    return c.json(
      {
        type: 'https://hoangsuphi.vn/errors/internal-server-error',
        title: 'Internal Server Error',
        status: 500,
        code: 'SYS_001',
        detail: responseDetail,
        instance,
        traceId,
        retryable: false,
      },
      500
    )
  }
}
```

### 1.3 Lý do lựa chọn

| Quyết định thiết kế | Lý do lựa chọn |
|:---|:---|
| **RFC 7807** | Định dạng Problem Details chuẩn hóa đã được thông qua bởi IETF, giúp các client (Web, Mobile) dễ dàng viết các thư viện xử lý lỗi dùng chung và tạo tính nhất quán cao cho tài liệu API OpenAPI/Swagger. |
| **Kế thừa Class `Error`** | Giữ lại đầy đủ cơ chế thu thập Call Stack mặc định của JavaScript engines, giúp các tool như Sentry dễ dàng trace ngược dòng code phát sinh lỗi. |
| **Phân cấp log (4xx vs 5xx)** | Tránh làm ô nhiễm màn hình dashboard log. Trong thực tế production, 401 (Unauthenticated) và 404 (Not Found) xảy ra hàng triệu lần do bot quét hoặc người dùng nhập sai, log chúng ở mức ERROR sẽ kích hoạt false-alarm (cảnh báo giả) làm phiền team vận hành. |
| **Dùng Custom URI** | `type` trỏ đến link wiki/tài liệu của dự án giải thích chi tiết cách sửa lỗi đó cho frontend devs. |

### 1.4 Ưu điểm

- **Khả năng gỡ lỗi (DX) tuyệt vời:** Frontend developer nhận được thông báo lỗi chi tiết, có định dạng rõ ràng kèm link tài liệu hướng dẫn khắc phục cụ thể.
- **Vận hành an tâm:** Lỗi 5xx được phát hiện chính xác, kích hoạt Slack/PagerDuty ngay lập tức mà không bị lẫn lộn bởi các lỗi người dùng bấm sai.
- **Dễ dàng bảo trì:** Khi viết code nghiệp vụ ở Service layer, developer chỉ cần quăng lỗi bằng từ khóa `throw new NotFoundError("Homestay not found")`, không cần quan tâm đến cách viết response JSON hay import HTTP status codes.

---

### 1.5 Nhược điểm

- **Boilerplate lớn ban đầu:** Phải định nghĩa nhiều class file cho từng nhóm lỗi. Tuy nhiên việc này chỉ làm 1 lần ở Phase 2 (Foundation) và sử dụng vĩnh viễn cho toàn bộ các Phase sau.

---

### 1.6 Các lựa chọn khác đã xem xét

| Phương án | Vấn đề |
|:---|:---|
| **Trả lỗi dạng `{ success: false, error: "message" }`** | Quá đơn giản, không cung cấp đủ ngữ cảnh lỗi cho hệ thống lớn (thiếu field-level validation errors, type URIs, codes). |
| **Dùng chuỗi string code đơn giản** | Khó tích hợp với các hệ thống tự động sinh tài liệu (Swagger/OpenAPI) và khó cho client parse các lỗi dạng lồng nhau (nested validation errors). |
| **Trả mã lỗi trực tiếp từ Database** | Gây nguy cơ bảo mật nghiêm trọng (SQL Injection leaks, tiết lộ cấu trúc bảng DB). |

---

### 1.7 Vì sao không chọn

- **Dạng `{ success: false }`:** Đây là dạng thiết kế nghiệp dư, thường dùng cho các dự án nhỏ hoặc demo. Khi một form đăng ký có 10 fields lỗi, dạng này buộc client phải parse string hoặc tự mò lỗi, làm tăng độ phức tạp của frontend code. Chuẩn RFC 7807 giải quyết triệt để vấn đề này nhờ hỗ trợ các thuộc tính mở rộng như `invalidParams`.

---

### 1.8 Khả năng mở rộng

- **Sentry Integration:** Ở Phase 8 (Security) hoặc Phase 10 (Deployment), ta chỉ cần cắm Sentry SDK vào Global Error Handler để tự động bắt các lỗi 500 và đẩy stack trace lên Sentry dashboard cùng `requestId` và `correlationId`.
- **Localization (Đa ngôn ngữ lỗi):** Có thể mở rộng bằng cách thêm middleware dịch message lỗi dựa trên header `Accept-Language` của client trước khi trả phản hồi RFC 7807.

---

### 1.9 Best Practices

- **Luôn `throw` đúng Exception Class:** 
  - Khi không tìm thấy dữ liệu: `throw new NotFoundError(...)`
  - Khi trùng lặp email: `throw new ConflictError(...)`
  - Khi param truyền sai định dạng: `throw new ValidationError(...)`
- **Không dùng Exception để kiểm soát luồng nghiệp vụ thông thường:** Chỉ dùng Exception cho các trường hợp thực sự bất thường hoặc lỗi dữ liệu đầu vào.
- **Che giấu stack trace ở production:** Đảm bảo `isProd` hoạt động chính xác để tránh rò rỉ dữ liệu hệ thống.
