## 1. MỤC TIÊU

Thiết kế các giải pháp và cơ chế kiểm soát an toàn bảo mật (Security Controls) thiết thực nhất cho **Identity Module** nhằm:
- Đảm bảo tính bí mật và toàn vẹn của thông tin xác thực (Credentials) và phiên làm việc (Sessions) của người dùng.
- Ngăn ngừa các lỗ hổng bảo mật phổ biến của OWASP (XSS, CSRF, Brute Force, Mass Assignment) ảnh hưởng tới IAM context.
- Xác lập ma trận phân quyền dựa trên vai trò (RBAC matrix) tĩnh, tối giản và hiệu quả nhất cho website du lịch cấp huyện (Admin, Editor, Tourist).
- Thiết lập các rào cản phòng vệ chiều sâu (Defense-in-depth) ở mức API Gateway (CORS, Rate Limiter, Security Headers) để bao bọc module an toàn.

## 2. THIẾT KẾ CÁC BIỆN PHÁP BẢO MẬT THIẾT YẾU

Hệ thống bảo mật của Identity Module dựa trên 5 trụ cột cốt lõi:

```
                  ┌────────────────────────────────────────┐
                  │           API Gateway / CORS           │
                  └──────────────────┬─────────────────────┘
                                     ▼
                  ┌────────────────────────────────────────┐
                  │       Rate Limiting (/auth/login)      │
                  └──────────────────┬─────────────────────┘
                                     ▼
                  ┌────────────────────────────────────────┐
                  │    HTTP Secure Cookies (HttpOnly)      │
                  └──────────────────┬─────────────────────┘
                                     ▼
                  ┌────────────────────────────────────────┐
                  │     JWT Access Token & PostgreSQL      │
                  └──────────────────┬─────────────────────┘
                                     ▼
                  ┌────────────────────────────────────────┐
                  │   Bun Native Bcrypt Password Hashing   │
                  └────────────────────────────────────────┘
```

---

### 2.1 Password Hashing

- **Cơ chế:** Sử dụng Bun native password hashing API (`Bun.password`).
- **Thuật toán:** Bcrypt với độ phức tạp mặc định là `rounds = 12`.
- **Lợi ích:** Bcrypt tự động sinh Salt ngẫu nhiên và băm mật khẩu một chiều an toàn, chống lại tấn công Rainbow Table. Bun native API chạy bằng C++ tối ưu cao, giảm thời gian xử lý CPU trên server và hạn chế nguy cơ nghẽn I/O khi có lượng lớn request login đồng thời.

---

### 2.2 Token & Session Management

- **Access Token (JWT):**
  - Thời gian sống: **15 phút** (Ngắn hạn).
  - Thuật toán ký: **HS256** với Khóa bí mật JWT dài tối thiểu 32 ký tự ngẫu nhiên.
  - Lưu trữ: Client lưu Access Token trong bộ nhớ RAM của Javascript (không ghi xuống LocalStorage/SessionStorage) để chống lại lỗ hổng chiếm đoạt token qua XSS.
  - Payload: Chứa `userId`, `sessionId`, `role`, `permissions`, `permissionsVersion`.

- **Refresh Token (Database-backed Session):**
  - Thời gian sống: **30 ngày** (Dài hạn).
  - Lưu trữ Database: Chỉ lưu trữ SHA-256 hash của Refresh Token (`user_sessions.token_hash`), tuyệt đối không lưu text thuần.
  - Vận chuyển mạng: Được truyền tự động thông qua **HTTP Cookie** đi kèm 4 thuộc tính bảo mật cao:
    1. `HttpOnly`: Trình duyệt cấm hoàn toàn script Javascript truy cập cookie này, triệt tiêu nguy cơ trộm token qua XSS.
    2. `Secure`: Chỉ truyền tải cookie qua kênh mã hóa HTTPS (ngoại trừ môi trường dev localhost).
    3. `SameSite=Strict`: Ngăn chặn trình duyệt gửi cookie đi kèm trong các request chéo trang (Cross-Origin), loại bỏ hoàn toàn nguy cơ tấn công CSRF.
    4. `Path=/api/v1/auth`: Thu hẹp phạm vi gửi cookie chỉ cho router auth, giảm thiểu phơi nhiễm token không cần thiết.

---

### 2.3 Brute-Force Prevention

- **Cơ chế:** Khóa tài khoản tạm thời dựa trên số lần đăng nhập sai (Failed Attempts).
- **Quy tắc:**
  - Nếu đăng nhập thất bại liên tiếp 5 lần → Cập nhật `lockoutUntil = Date.now() + 15 phút` vào bản ghi của user.
  - Trong thời gian khóa, mọi yêu cầu login của tài khoản này đều bị từ chối lập tức ở lớp Service mà không cần kiểm tra lại password (tiết kiệm tài nguyên xử lý CPU băm bcrypt).

---

### 2.4 API Gateway & HTTP Security Headers

- **Helmet (Security Headers):** Hono nạp sẵn middleware Helmet để thiết lập các HTTP headers tiêu chuẩn:
  - `Content-Security-Policy (CSP)`: Giới hạn nguồn tài nguyên script được phép tải.
  - `X-Frame-Options: DENY`: Chống tấn công Clickjacking.
  - `X-Content-Type-Options: nosniff`: Ngăn chặn MIME-type sniffing.
  - `Strict-Transport-Security (HSTS)`: Bắt buộc trình duyệt chỉ kết nối HTTPS.

- **CORS Protection:** Cấu hình CORS whitelist giới hạn truy cập từ domain chính thức `hoangsuphi.vn` và subdomain admin:
  - `Origin`: `https://hoangsuphi.vn`, `https://admin.hoangsuphi.vn`.
  - `Credentials`: `true` (Cho phép truyền nhận HTTP Cookie).

- **Rate Limiting:** Áp dụng rate limiter trực tiếp trên Endpoint login thông qua cấu hình môi trường linh hoạt:
  - `LOGIN_RATE_LIMIT_MAX = 10` (Số lượng request tối đa)
  - `LOGIN_RATE_LIMIT_WINDOW = 60s` (Cửa sổ thời gian tính bằng giây)
  - Giới hạn chạy theo địa chỉ IP của Client để ngăn chặn tấn công brute-force mật độ lớn.


---

### 2.5 Role-Based Access Control (RBAC Matrix)

Ở quy mô MVP cấp huyện, hệ thống phân chia thành 3 vai trò tĩnh:

| Quyền hạn (Permission) | Khách du lịch (Tourist) | Biên tập viên (Editor) | Quản trị viên (Admin) |
|:---|:---:|:---:|:---:|
| `user:read` (Xem profile cá nhân) | ✅ | ✅ | ✅ |
| `user:write` (Cập nhật profile cá nhân) | ✅ | ✅ | ✅ |
| `article:create` (Tạo bài viết) | ❌ | ✅ | ✅ |
| `article:publish` (Xuất bản bài viết công khai) | ❌ | ❌ | ✅ |
| `system:write` (Quản trị hệ thống, đổi cấu hình) | ❌ | ❌ | ✅ |

- **Zero I/O Authorization Checking:** Mảng permissions được nhúng trực tiếp vào payload của Access Token. Khi middleware `requirePermission('article:create')` kiểm tra, nó chỉ cần decode token trực tiếp trên RAM, không sinh bất kỳ query đọc DB hay Redis nào, tối đa hóa performance.

## 3. KHẢ NĂNG MỞ RỘNG (FUTURE ENHANCEMENTS)

- **MFA (Multi-Factor Authentication):** Trong tương lai khi mở rộng lên quy mô tỉnh, ta có thể bổ sung cột `two_factor_secret` trong bảng `users`. Khi login thành công bước 1, token trả về sẽ có trạng thái `"status": "awaiting_mfa"`. Các API nghiệp vụ khác sẽ từ chối truy cập cho đến khi người dùng gọi API `/auth/mfa/verify` để hoàn tất xác thực 2 lớp.
- **Dynamic Permissions:** Dịch chuyển RBAC từ bảng tĩnh sang mapping dữ liệu trong DB (bảng `permissions`, `role_permissions`) khi số lượng roles tăng lên nhiều mà không cần thay đổi logic middleware kiểm tra quyền.
