## 2. Confirmed defects fixed

### 2.1 Concurrent dedup response disclosure

`ScopedDuplicateConflictError` can contain the internal hash and uploader identifier. `MediaIngestionService` no longer forwards that repository message to the public `ConflictError`; it returns a fixed client-safe conflict message.

Evidence:

- HTTP regression forces the repository conflict with sentinel hash/uploader values.
- Response is HTTP 409.
- Serialized response contains neither sentinel, hash, uploader nor constraint name.

### 2.2 Sensitive exception logging

Media ingestion no longer logs raw database, provider, transition, cleanup or post-finalization errors. Logs contain only a safe error class and operation context.

Evidence:

- Unit tests inject database and Cloudinary sentinel secrets.
- Logger calls are captured.
- Serialized log arguments do not contain either secret.
- Public responses retain the approved safe error message.

### 2.3 Real repository integration isolation

The non-standard `media.repository.ts?real` import was removed. The normal typed repository import is used.

The global Media repository mock is disabled only for the dedicated integration command by setting `MEDIA_REPOSITORY_INTEGRATION=1` before Bun loads its preload file. Unit and HTTP suites continue to use the existing isolated mock.

Dedicated command:

```powershell
$env:MEDIA_REPOSITORY_INTEGRATION='1'
$env:MEDIA_TEST_DATABASE_URL='postgres://postgres:***@localhost:5432/hoangsuphi_media_test'
bun test src/modules/media/repository/media.repository.integration.test.ts
```

### 2.4 Cloudinary smoke hardening

The real-provider smoke run exposed and verified fixes at the adapter boundary:

- The integration test no longer lets cleanup errors hide an earlier upload/download failure.
- Upload and delete provider errors are reduced to safe error class, HTTP code and allowlisted reason; raw provider messages and credentials are never logged.
- Redundant upload invalidation was removed because a new upload uses `overwrite: false`.
- `exists()` recognizes both direct `http_code` and the nested Admin API SDK error shape, so a post-delete 404 correctly maps to `false`.
- Provider result variants `not found` and `not_found` are handled idempotently.

### 6.1 Production CDN consideration

The smoke proves physical origin deletion: Cloudinary's resource lookup returns nested 404 and the adapter maps it to `exists() === false`. The current adapter does not request CDN invalidation during compensation cleanup. This is consistent with the approved contract, which does not promise immediate public-URL revocation on soft delete, and compensation assets are never returned as READY URLs.

Step 4.3.7 must explicitly confirm the production purge policy: either enable Cloudinary CDN invalidation for purge operations or document the accepted cache-retention behavior. This consideration does not invalidate the Step 4.3.6 origin-cleanup gate.
