## 1. MỤC TIÊU

Thiết kế cấu trúc thư mục chi tiết cho **Identity Module** nhằm:
- Phản ánh đúng đắn kiến trúc phân lớp (Layered + Ports & Adapters hybrid) đã khóa ở `02.01` trong phạm vi module thực tế.
- Phân tách rạch ròi 2 miền trách nhiệm nghiệp vụ (Bounded Context contexts):
  - **`auth`**: Chịu trách nhiệm xác thực danh tính, quản lý JWT token, RTR, và phiên làm việc (Sessions).
  - **`users`**: Chịu trách nhiệm quản lý thông tin tài khoản người dùng, profile cá nhân (`/users/me`), và RBAC authorization data.
- Enforce luật import một chiều giữa các file để loại bỏ hoàn toàn nguy cơ import vòng tròn (circular dependencies) và đảm bảo code nghiệp vụ không bị dính chặt vào database driver (Drizzle).

## 2. THIẾT KẾ CẤU TRÚC THƯ MỤC CHI TIẾT

Identity Module nằm hoàn toàn trong thư mục `apps/backend/src/modules/` và được tổ chức thành 2 feature folders song song:

```
apps/backend/src/modules/
│
├── auth/                                  ← Feature 1: Authentication & Sessions
│   ├── index.ts                           ← Export Public interface / router của module
│   ├── auth.route.ts                      ← Presentation Layer: Hono routes & Handler
│   ├── auth.dto.ts                        ← Presentation Layer: Input/Output Zod Schemas
│   ├── auth.service.ts                    ← Application Layer: Orchestrate logic auth
│   ├── auth.repository.ts                 ← Infrastructure Layer: DB Drizzle/Redis adapter
│   │
│   └── domain/                            ← Domain Layer: Logic nghiệp vụ thuần
│       ├── session.entity.ts              ← UserSession Entity
│       └── value-objects/
│           └── fingerprint.vo.ts          ← ClientFingerprint Value Object
│
├── users/                                 ← Feature 2: User Profiles & RBAC Management
│   ├── index.ts                           ← Export Public interface / router của module
│   ├── users.route.ts                     ← Presentation Layer: Hono routes & Handler (/me)
│   ├── users.dto.ts                       ← Presentation Layer: Zod Input/Output schemas
│   ├── users.service.ts                   ← Application Layer: Business logic profile & role
│   ├── users.repository.ts                ← Infrastructure Layer: DB Drizzle adapter
│   │
│   └── domain/                            ← Domain Layer: Logic nghiệp vụ thuần
│       ├── user.aggregate.ts              ← User Aggregate Root Entity
│       ├── profile.entity.ts              ← UserProfile Entity
│       ├── events/
│       │   └── user.events.ts             ← Domain Events (Reserved)
│       └── value-objects/
│           ├── email.vo.ts                ← Email Value Object
│           ├── password.vo.ts             ← Password Value Object
│           └── password-history.vo.ts     ← PasswordHistory Value Object
```

## 3. KIẾN TRÚC IMPORT & DEPENDENCY RULES

Để đảm bảo ranh giới cô lập (module boundaries) và phân tách tầng sạch sẽ:

```
Tầng Trình diễn (Routes/DTOs) ──> Tầng Ứng dụng (Services) ──> Tầng Domain (Entities/VOs)
                                       │
                                       └───> Tầng Hạ tầng (Repository Interfaces)
                                                    ▲
                                                    │ (Hiện thực hóa)
                                             Tầng Hạ tầng (Repository Drizzle/Redis)
```

### 1. Quy tắc nhập (Import Rules)

- **Domain Layer (`domain/`)**:
  - Không được import bất kỳ file nào từ các thư mục cha hoặc thư mục module khác.
  - Chỉ phụ thuộc vào các thư viện thuần (như `zod` để validate nhỏ, crypto helper của Bun).
  - ❌ *Cấm tuyệt đối:* `import { db } from '@/lib/database/client'` hoặc `import { authService } from '../auth.service'`.

- **Application Layer (`services`)**:
  - Chỉ import từ `domain/` của chính module đó.
  - Phụ thuộc vào `Repository` thông qua Dependency Injection (hoặc instantiation lớp repository adapter).
  - ❌ *Cấm tuyệt đối:* Import Hono `Context` hoặc gửi phản hồi HTTP trực tiếp từ Service.

- **Presentation Layer (`routes/handlers/dtos`)**:
  - Nhận HTTP Request, gọi validator middleware, nạp dữ liệu sạch và gọi hàm của `Service`.
  - Phụ thuộc vào Hono `Context` (`c.json`, `c.req.valid`).

## 4. LUỒNG DỮ LIỆU & GIAO TIẾP INTER-MODULE

Khi một module nghiệp vụ bên ngoài (ví dụ: `articles` hoặc `businesses`) cần thông tin định danh của user:
- **Không được gọi trực tiếp `usersService` hay `authService`**.
- Thông tin định danh `JwtPayload` (userId, sessionId, permissions) đã được nạp tự động vào context router qua middleware `authenticate()` tại `app.ts` ở Hono framework level.
- Handler chỉ cần lấy ra qua: `const user = c.get('user')`.

---

## 5. BEST PRACTICES

- **Co-location (Sắp đặt liền kề):** Giữ toàn bộ tệp tin kiểm thử unit test (`.spec.ts` hoặc `.test.ts`) ngay sát bên tệp tin code nguồn (ví dụ: `user.aggregate.ts` đi kèm `user.aggregate.test.ts`). Điều này tăng tốc độ viết test và DX đáng kể.
- **Index Exports (Tập trung hóa cổng ra):** Sử dụng `auth/index.ts` để re-export những thứ bên ngoài được quyền dùng (như router, middleware authenticate). Không cho phép module khác import sâu vào bên trong thư mục như `import { User } from '@/modules/users/domain/user.aggregate'`.
- **Cấu trúc Feature Folder chuẩn hóa (Toàn dự án):** Nhằm đảm bảo tính đồng nhất tối đa, bất kỳ feature module nào trong dự án (IAM, Regions, Tourism, Content...) đều phải tuân theo cấu trúc tổ chức tệp tin đầy đủ dưới đây khi phát sinh nghiệp vụ:
  ```
  [feature]/
  ├── domain/         ← Domain Entities, Value Objects, Domain Events
  ├── dto/            ← Zod schemas & types
  ├── repository/     ← Interfaces & Drizzle implementations
  ├── service/        ← Application logic
  ├── route/          ← Hono router & handlers
  ├── middleware/     ← Module-specific middlewares
  ├── errors/         ← Custom module exception classes
  └── index.ts        ← Public gateway (Chỉ export Route & Public Services/Types)
  ```
- **Cấm Barrel Export (`export *`) chéo Module:** Nhằm tránh rủi ro phụ thuộc ngầm (transitive dependencies), hỗ trợ Bun tree-shaking tối đa, và tránh lỗi runtime do import chéo vòng tròn:
  - Chỉ sử dụng `export *` nội bộ trong cùng một feature folder (ví dụ: `domain/index.ts` re-export các entities cùng thư mục).
  - TUYỆT ĐỐI CẤM sử dụng `export *` từ module này sang module khác. Giao tiếp chéo module chỉ được phép import tường minh từ API gateway `index.ts` của module đích (Ví dụ: `import { authenticate } from '@/modules/auth'`).

## 6. KHẢ NĂNG MỞ RỘNG

- **Dịch chuyển Microservices:** Khi lượng traffic IAM tăng đột biến, ta chỉ cần cắt nguyên thư mục `auth` và `users` này chuyển sang một repo/project mới chạy độc lập (ví dụ sử dụng NestJS hoặc Hono trên Cloudflare Workers) mà không sợ bị gãy các dependencies của các module khác, vì giao tiếp inter-module hoàn toàn là qua HTTP request headers (Access Token).


---

## 7. CÁC LỰA CHỌN KHÁC ĐÃ XEM XÉT

| Phương án | Vấn đề |
|:---|:---|
| **Cấu trúc phẳng (Flat structure)** | Gộp chung tất cả file của `auth` và `users` vào một thư mục `identity`. Điều này làm số lượng tệp tin tăng vọt lên 15-20 file trong 1 folder, gây khó khăn cho việc định vị code và khó bảo trì. |

---

## 8. VÌ SAO KHÔNG CHỌN

- **Flat structure:** Identity Module thực chất chứa 2 nghiệp vụ độc lập về mặt dữ liệu: Quản lý token/session (hạ tầng xác thực) và Quản lý thông tin hồ sơ/RBAC (nghiệp vụ lưu trữ tài khoản). Phân rã thành 2 folders `auth` và `users` giúp phân định rõ nhiệm vụ của từng service và repository, giúp cấu hình database schema gọn gàng hơn.
