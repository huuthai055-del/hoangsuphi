## 1. MỤC TIÊU

Thiết kế cấu trúc Domain cho **Regions Module** nhằm:
- Định nghĩa mô hình phân cấp địa lý hành chính (Huyện → Xã → Bản/Thôn) sử dụng cấu trúc đường dẫn phân cấp `ltree` của PostgreSQL, sẵn sàng mở rộng quy mô toàn quốc trong tương lai mà không cần cấu trúc lại dữ liệu.
- Thiết lập ranh giới (Domain Boundaries), thực thể (Entities), Value Objects và quy tắc nghiệp vụ (Business Rules) liên quan đến vùng địa lý và điểm địa danh du lịch (`TouristPlace`).
- Đảm bảo các thuộc tính tọa độ địa lý (GPS) được thiết kế type-safe sử dụng kiểu dữ liệu PostGIS `geography(Point, 4326)`.
- Xác định quy tắc xử lý Soft Delete và tính toàn vẹn dữ liệu cha-con trong cây phân cấp.

## 2. THIẾT KẾ DOMAIN MODEL

### 2.1 Bounded Context: Geographical & Tourism Resources (Geo Context)

Geo Context chịu trách nhiệm quản lý phân cấp hành lý địa lý và tọa độ không gian các địa điểm.

```
┌────────────────────────────────────────────────────────────────────────┐
│                          Geo Context                                   │
│                                                                        │
│   ┌─────────────────┐ 1:N Parent-Child ┌─────────────────────────┐     │
│   │     Region      │◄─────────────────┤       TouristPlace      │     │
│   │    (Entity)     │                  │         (Entity)        │     │
│   └────────┬────────┘                  └────────────┬────────────┘     │
│            │ 1:1                                    │ 1:1              │
│   ┌────────┴────────┐                  ┌────────────┴────────────┐     │
│   │    LtreePath    │                  │       GPSLocation       │     │
│   │ (Value Object)  │                  │      (Value Object)     │     │
│   └─────────────────┘                  └─────────────────────────┘     │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.2 Domain Entities & Aggregates

#### 1. Aggregate Root: Region
Thực thể duy nhất đại diện cho mọi cấp đơn vị địa lý (Huyện, Xã, Thôn/Bản). Thiết kế này nhất quán hoá cấu trúc quản lý cây phân cấp địa lý.
- **Attributes:**
  - `id`: UUIDv7 (Định danh độc bản)
  - `parentId`: UUIDv7 | null (Tham chiếu ngược tới nút cha trực tiếp)
  - `name`: string (Tên đơn vị: "Bản Phùng", "Hoàng Su Phì")
  - `slug`: string (Slug: "ban-phung", "hoang-su-phi")
  - `path`: LtreePath (Value Object - Phân cấp hành lý ltree, bắt đầu bằng tỉnh)
  - `level`: RegionLevel (Enum: `PROVINCE`, `DISTRICT`, `COMMUNE`, `VILLAGE`)
  - `center`: GPSLocation | null (Value Object - Tọa độ trung tâm)
  - `description`: string | null
  - `status`: RegionStatus (Enum: `ACTIVE`, `INACTIVE`)
  - **Audit & Soft Delete Fields:**
    - `createdAt`: Date
    - `updatedAt`: Date
    - `deletedAt`: Date | null (Hỗ trợ soft delete)
- **Domain Methods:**
  - `deactivate()`: Chuyển trạng thái sang `INACTIVE`.
  - `softDelete()`: Đánh dấu `deletedAt = new Date()`.
  - `isRoot()`: Kiểm tra nếu là nút gốc (Province - Hà Giang).
  - `getParentPath()`: Lấy path của nút cha trực tiếp từ ltree path.

#### 2. Entity: TouristPlace
Đại diện cho một điểm tham quan, địa danh du lịch cụ thể nằm trong một vùng địa lý (ví dụ: Đồi mâm xôi Bản Phùng, Đỉnh Chiêu Lầu Thi).
- **Attributes:**
  - `id`: UUIDv7
  - `regionId`: UUIDv7 (Tham chiếu tới Region cấp Commune hoặc Village tương ứng)
  - `name`: string (Tên điểm: "Ruộng bậc thang Bản Phùng")
  - `slug`: string (Slug: "ruong-bac-thang-ban-phung")
  - `location`: GPSLocation (Value Object - Tọa độ GPS chính xác)
  - `description`: string | null
  - `coverUrl`: string | null (Ảnh bìa địa danh)
  - `status`: PlaceStatus (Enum: `ACTIVE`, `INACTIVE`)
  - **Audit & Soft Delete Fields:**
    - `createdAt`: Date
    - `updatedAt`: Date
    - `deletedAt`: Date | null

### 2.3 Value Objects

#### 1. LtreePath
Đại diện cho đường dẫn phân cấp địa lý trong cây thư mục `ltree`.
- **Định dạng:** Các nhãn (labels) phân tách bằng dấu chấm `.`. Không sử dụng mã quốc gia `vn`. Bắt đầu trực tiếp bằng cấp tỉnh.
  - *Ví dụ:* `ha_giang.hoang_su_phi.ban_phung`
- **Quy tắc chuyển hóa (ltree label constraint):**
  - PostgreSQL ltree chỉ chấp nhận các ký tự chữ, số và dấu gạch dưới `_`.
  - Nhãn **không** được phép chứa dấu gạch ngang `-`. Do đó, Value Object `LtreePath` bắt buộc phải tự động chuyển đổi các ký tự `-` trong slug thành `_`.
  - *Ví dụ:* Huyện `"hoang-su-phi"` sẽ được lưu trữ trong path là `"hoang_su_phi"`.

#### 2. GPSLocation
Đại diện cho tọa độ địa lý không gian (Kinh độ, Vĩ độ) sử dụng hệ tọa độ WGS84 (EPSG:4326).
- **Attributes:**
  - `lng`: number (Kinh độ, giá trị từ -180 đến 180)
  - `lat`: number (Vĩ độ, giá trị từ -90 đến 90)
- **Phương thức:**
  - `toWkt()`: Chuyển đổi sang định dạng Well-Known Text (`POINT(lng lat)`) để lưu xuống cột PostGIS `geo- **Phân cấp ltree chuẩn hóa (Tỉnh -> Huyện -> Xã -> Bản/Thôn):**
  - Mặc dù MVP hiện tại chỉ phục vụ cho Hoàng Su Phì, cấu trúc path ltree vẫn phải bắt đầu bằng mã tỉnh để bảo vệ khả năng scale chéo tỉnh trong tương lai.
  - Cấu trúc path chuẩn: `[tinh].[huyen].[xa].[ban]` (Ví dụ: `ha_giang.hoang_su_phi.ban_phung`).
- **PostGIS geography(Point, 4326):** Dữ liệu tọa độ GPS bắt buộc phải lưu dạng `geography` thay vì `geometry` để đảm bảo các phép tính toán khoảng cách (ví dụ: tìm homestay trong bán kính 2km từ điểm du lịch) đạt độ chính xác thực tế tính bằng mét trên bề mặt cong của Trái Đất.
- **Cascade Deactivation:** Khi deactivate hoặc soft-delete một Region cha (ví dụ: Huyện Hoàng Su Phì), hệ thống sẽ không tự động xóa DB của con nhưng logic Repository phải loại bỏ các con khỏi kết quả đọc thông qua kiểm tra path.

## 6. KHẢ NĂNG MỞ RỘNG (FUTURE ENHANCEMENTS)

- **Mở rộng toàn quốc:** Khi hệ thống scale lên toàn quốc, ta chỉ cần insert dữ liệu tỉnh mới (ví dụ: `cao_bang.trung_khanh.ban_gioc`) mà không cần thay đổi bất kỳ chỉ mục, bảng biểu hay câu lệnh SQL query hiện tại, vì toán tử `<@` (is ancestor of) của ltree xử lý phân cấp động cực kỳ mạnh mẽ.

## 7. CÁC LỰA CHỌN KHÁC ĐÃ XEM XÉT

| Phương án | Vấn đề |
|:---|:---|
| **Tách bảng Province, District, Commune, Village** | Phải duy trì 4 bảng, 4 bộ CRUD, 4 Services và Repositories riêng biệt, gây ra sự cồng kềnh cực lớn và khó khăn khi thực hiện các câu JOIN phân cấp. |

## 8. VÌ SAO KHÔNG CHỌN

- **Tách bảng:** Việc gom chung vào một thực thể `Region` thống nhất giúp tối giản hóa mã nguồn và cấu trúc bảng của MVP cấp huyện, đồng thời cho phép tạo ra một bộ API quản lý địa lý duy nhất cho toàn dự án.
- **Adjacency List thuần túy:** Gây suy giảm hiệu năng nghiêm trọng khi truy vấn lấy danh sách con nhiều cấp. Sử dụng `ltree` kết hợp `parentId` mang lại DX tốt nhất và tốc độ sub-millisecond.

## 8. VÌ SAO KHÔNG CHỌN

- **Adjacency List:** Mặc dù Adjacency List rất dễ cài đặt ở giai đoạn đầu, nó là một cơn ác mộng về hiệu năng khi cần truy vấn lấy danh sách nhiều cấp (ví dụ: lấy mọi Homestay/Điểm du lịch thuộc huyện Hoàng Su Phì - bao gồm tất cả các xã, thôn con). Dùng `ltree` cho phép ta lấy toàn bộ các nút con chỉ bằng một câu query index duy nhất (`path <@ 'vn.ha_giang.hoang_su_phi'`), tốc độ thực thi nhanh gấp 10-50 lần so với đệ quy SQL.
